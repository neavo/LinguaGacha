# 测试审查与整理

只在任务要求审查、合并、清理、重构测试或评估测试价值时读取本文件。

## 审查目标

让保留的测试准确证明当前行为，并使组织方式符合仓库约定。覆盖率、文件数量和测试数量只是信号，不是目标。

## 建立事实清单

先列出：

- 请求涉及的行为、入口和状态拥有者；
- 相关实现、现有测试、夹具和 helper；
- 单元、集成、契约、端到端等测试层级；
- 测试命令、配置、CI 分组和历史缺陷证据。

不要预设测试文件必须与实现文件一一对应。组织方式应让行为和测试层级易于定位，并遵循项目已有规则。

合理分层示例：

```text
src/invoice.py
tests/unit/test_invoice_total.py
tests/contracts/test_invoice_export.py
```

两个测试文件都触及 `invoice.py` 并不构成重复：前者证明金额规则，后者必须调用真实导出入口并证明公开载荷。若后者只在测试里手拼字典再断言同一金额，就应删除或改写。

## 逐用例判断

每个测试回答四个问题：

1. 它证明哪条当前有效的行为、边界或历史缺陷？
2. 主要断言是公开结果，还是偶然实现细节？
3. 场景能否从公开入口、协议或真实运行路径触达？
4. 删除或弱化它会失去什么风险防护？
5. 如果某个字面量被合理调优，而协议、边界和业务语义均未改变，这个测试是否仍应失败？

结论使用以下类别：

- **保留**：行为价值明确，写法稳定。
- **修改**：目标有价值，但断言、准备或隔离方式脆弱。
- **合并**：与其他用例重复，合并后仍能清楚定位失败。
- **拆分**：混合了不同测试层级或多个独立失败原因。
- **删除**：过时、重复、不可触达且没有历史风险价值，或只服务覆盖率数字。

精确值由协议、格式、迁移、历史兼容或安全要求定义时保留；行为有价值但预期值只是从调优常量机械派生时改测关系或边界；直接比较导出常量与手写字面量且没有第二权威来源时删除。

分类示例：

| 现状 | 结论 |
| --- | --- |
| 历史缺陷回归，断言公开结果 | 保留 |
| 有价值场景只检查私有缓存 | 修改为公开结果 |
| 三个用例只替换无语义 ID | 合并或参数化 |
| 一个测试同时覆盖保存、通知和重试 | 按独立失败原因拆分 |
| 测试内伪造不存在的“导出结果” | 删除，或改测真实导出入口 |

## 组织测试

- 按行为、测试层级、执行成本和维护责任组织，不强求实现文件与测试文件一一对应。
- 只有失败原因、运行成本或责任边界确实不同才拆分；同一行为的平行测试优先合并。

## 业务透明重构

测试难写时，先判断根因是否是副作用和规则缠在一起。必要时可：

- 提取纯函数；
- 注入 clock、ID、transport 或 repository；
- 收口重复分支；
- 返回更明确的公开结果。

不要为了 mock 暴露私有状态、增加只服务测试的生产入口，或改变默认值、错误和持久化语义。

透明重构示例：

| 重构前 | 合理重构 | 越界做法 |
| --- | --- | --- |
| 过期规则直接读取系统时间，测试只能深层 patch | 提取 `is_expired(expires_at, now)`，生产入口仍传入当前时间 | 为测试增加跳过校验开关 |
| 业务规则与 HTTP 写入混在同一函数 | 提取纯规则，保留原调用顺序和错误语义 | 修改失败重试或默认返回值 |

## 推荐顺序

1. 建立事实清单并运行现有目标测试。
2. 标记重复、白盒、脆弱、昂贵和失效用例。
3. 先删除确认无价值的重复，再修改有价值但不稳定的测试。
4. 只有组织边界清楚时才合并或拆分文件。
5. 必要时做最小业务透明重构。
6. 运行目标测试和受影响套件，比较失败信息与执行成本。
7. 交付时分别说明保留、修改、合并、拆分和删除的内容及依据。
