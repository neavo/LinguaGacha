# Project Test 技能验收

只在维护或验收 `project-test` 技能时读取本文件。使用宿主现有的技能选择或评测能力，不绑定特定模型、平台字段或分发方式。

## 验收方法

1. 在没有维护结论和预期答案的新上下文中提交原始请求。
2. 支持自动技能选择时记录是否加载本技能；不支持时显式调用技能，只验证执行行为。
3. 记录实际读取的项目事实、所选测试层级、编辑范围、验证命令、失败分类和交付结果。
4. 对关键用例重复执行，检查决策是否稳定；不要求措辞完全一致。

## 触发用例

应触发：

- “给订单金额规则补一组单元测试。”
- “这个 Vitest 偶尔失败，帮我找出不稳定原因并修好。”
- “审查这批旧测试，指出重复、白盒断言和无价值覆盖。”
- “事件载荷新增字段，请补齐生产者和消费者的契约测试。”
- “整理这些夹具和 helper，但不要改变业务行为。”

不应触发：

- “解释这段业务代码做了什么。”
- “手工检查页面配色和间距。”
- “汇总生产环境最近一小时的日志。”
- “把这份需求说明翻译成英文。”

若明显相关请求未触发，优先补充 `description` 中的用户措辞；若无关请求触发，先确认是否确有自动化测试意图，再收窄范围。

## 功能用例

| 场景 | 必须观察到的行为 |
| --- | --- |
| 新增测试 | 读取仓库规则和相邻测试；选择最低有效层级；不为示例新增依赖 |
| 缺陷回归 | 可复现时保留修复前失败、修复后通过的证据；修复共享根因而非单一路径症状 |
| 只读审查 | 不编辑文件；发现包含位置、证据和影响；候选信号不会直接写成缺陷 |
| 测试整理 | 保持业务行为；每个保留、修改、合并、拆分或删除决定都有依据 |
| 跨边界变化 | 找到契约拥有者；覆盖生产者和消费者；真实集成只覆盖无法由契约测试证明的风险 |
| 验证失败 | 区分本次引入、既有、环境和不稳定失败；报告未验证范围，不削弱断言 |

## 通过条件

- 明显相关和改写后的请求均按预期触发，无关请求不触发。
- 各功能用例遵守任务授权、最低有效层级、副作用隔离和验证门。
- 重复执行时，测试层级、编辑边界和失败分类没有无证据漂移。
- 与不使用技能的基线相比，不增加无关依赖、测试层级、工具调用或用户纠正。

## 迭代顺序

1. 漏触发或误触发：调整 `description`，不要先扩写正文。
2. 工作流遗漏：修改 `SKILL.md` 的步骤或验证门。
3. 特定技术栈失误：只修改对应引用文件。
4. 同一操作反复手写且需要确定性：再考虑增加最小脚本。
5. 修改后重新运行相关触发与功能用例，并记录仍未覆盖的宿主差异。
