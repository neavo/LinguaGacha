# LinguaGacha 后端设计

后端负责工程事实与执行结果的一致性。GUI、CLI 和产品 Agent 的工程写入汇入同一提交流程。

- 进程、宿主生命周期与跨层不变量见 [ARCHITECTURE](ARCHITECTURE.md)。
- Agent 工作材料见 [AGENT_RUNTIME](AGENT_RUNTIME.md)。
- 源码与验证入口见 [WORKFLOW](WORKFLOW.md)。

## 💾 工程提交与恢复

`ProjectWriteStore` 在同一 `.lg` 事务中处理用户意图、重复条目协调、翻译统计和修订更新。直接修改与被动变化因此能一起进入缓存和事件。

一次提交分为三个阶段：

1. 提交数据库事务。
2. 更新缓存。
3. 发布公开通知。

工程修改可能先于 SDK 工具回执持久化。中断恢复按 [已提交事实优先](ARCHITECTURE.md#已提交事实优先) 处理，后续指令重新读取现值。

数据库提交后的同步失败使用 `data.committed_sync_failed`，携带已提交事实和重载要求。调用方重读数据，避免重复执行已经完成的写入。

HTTP 写入回包与 SSE 承载同一 `ProjectChangeEvent`，到达顺序不固定。前端的去重与恢复见 [FRONTEND](FRONTEND.md)。

### 冲突判断

|写入来源|判断依据|设计目的|
|---|---|---|
|基于查询快照的编辑|所依赖的 `sectionRevisions`|保护用户读到的内容|
|任务启动、按当前事实重置|取得占用后的工程事实|按执行时状态处理|
|Agent 的 `workspace_apply`|目标对象指纹 `fp`|允许长时间调查后提交少量对象，与无关修改共存|

`projectRevision` 汇总各分区修订的最大值。写入冲突仍按实际依赖的分区判断，不能把这个汇总值当成全局写锁。

Agent 提交的两种失败有不同结果：

- 对象冲突：拒绝冲突对象，其余合法对象可以在同一事务中提交。
- 数据库失败：回滚整批事实与修订。

后续工作以回执中实际应用的对象为准。

### 多个存储之间的补偿

应用设置、预设文件与 `.lg` 分别持久化，涉及多个存储的命令持有相应互斥。

- 提交前失败：补偿本次修改。
- 工程已提交后的同步失败：保留提交结果，按重载语义恢复。

补偿覆盖进程内失败，文件与配置之间仍存在崩溃窗口。恢复时需要读取当前持久化事实。

### 项目语言与应用预过滤开关

项目语言随 `.lg` 保留，使同一工程在不同应用配置下继续使用原来的翻译方向。`mtool_optimizer_enable` 与 `skip_duplicate_source_text_enable` 代表用户的预过滤偏好，项目内的值记录已采用的处理口径，因此打开工程时只对齐这两个开关。

## ⏳ 运行占用与任务完成

`RuntimeOperationGate` 协调翻译、Agent、模型接口测试和工程写入的占用，并遵循 [占用持续到收尾](ARCHITECTURE.md#占用持续到收尾)，避免旧请求仍在写入时启动下一操作。

Agent 内的批量翻译和工程提交复用当前 Agent 占用。

普通设置和模型配置允许在运行中修改，按 [执行内配置固定](ARCHITECTURE.md#执行内配置固定) 保持同一批请求的处理语义稳定。

### 进度口径

|口径|用途|保存边界|
|---|---|---|
|本轮 `run_progress`|展示本次目标的处理量与用量|当前运行的内存状态|
|工程累计 `progress`|工程重开后继续展示累计统计|随 `.lg` 持久化|
|工程完成率|判断当前工程条目的处理情况|根据当前已保存条目状态计算|

局部重翻的本轮进度不能替代工程完成率。

### 完成与重试

批量翻译逐批提交有效译文，取消或后续失败保留已有提交。重试预算仅属于本轮运行。

`completion` 等待规划、请求、写入和资源收尾完成。调用方用它决定后续译文生成或释放，快照负责展示。

恢复分为两类：

- 请求故障：网络调度器在原逻辑请求内等待密钥恢复。
- 内容失败：内容处理针对无效译文重试。

全部密钥不可用时，任务继续等待恢复或取消，前端展示后端提供的恢复状态。

### 计算线程

work-unit、planning 和 compute worker 承担计算，数据库与事件由后端持有。

work-unit 经父线程端口发送模型请求，使线程崩溃和取消能够终止同一次执行的网络请求。

## 📄 原稿、翻译与译文生成

资产拥有文件身份，避免空文件丢失类型。解析与入库共用原始字节，使持久定位始终对应固化原稿。

资产路径也是 Agent 原稿投影路径，因此名称既不能重复，也不能互为文件与目录。自动命名归导入准备所有，提交沿用确认的名称。已有资产身份保持稳定，时间戳只用于名称避让。

文本规则随格式、原文和文件上下文计算，避免条目保存的旧分类限制后续规则调整。跨文件译文继承仍区分规则类别。

`.lg` 保存原始资产和编辑事实，使原始输入文件移动后仍能继续工作。格式写回依赖工程中的原始资产，缺失时译文生成失败。

“全部重置”从已保存资产重新解析内容：

- 可能恢复源文件自带译文，并改变条目数。
- 所有资产通过文件级解析后才提交替换，避免留下半份重建结果。

### 译文生成的失败边界

GUI 与 CLI 共用译文生成服务：

- 格式计算或写回失败会终止本次生成，已经写出的文件可能保留。
- 打开输出目录属于完成后的附加动作，失败时保留已生成产物。

### 原生游戏

原生游戏的输入限制由共享来源发现统一维护，使新建工程、追加导入、CLI 和字体工具使用同一契约。入口限制与封装支持分开维护，游戏布局、配置、数据包与载体冲突由各引擎确认。

游戏目录占用独立于模型运行占用，使字体修改可以与模型任务并行。字体、导入和译文输出共享目录占用，防止重叠目录上的操作混用文件。

导入占用必须覆盖来源识别和原稿固化。解包事务结束时原稿与文件清单尚未固定，提前释放占用会让其他操作混入本批来源。用户确认期间释放预览占用，正式提交重新识别来源。此协调仅覆盖应用管理的操作，工作区脚本与外部程序遵循各自的文件边界。

一个游戏对应一个资产，独占译文输出目录，使整体替换和删除拥有一致边界。资产后缀表达引擎类型，ZIP 承担底层封装，历史 `.zip` 资产保持原身份。容器清单独立于翻译条目，保证零条目和解析失败文件仍能生成译文。译文继承允许在工程范围内跨游戏匹配。

导入时确定附加原稿，并随资产保存清单 `additional_files`。解析失败和零条目不改变成员归属。资产与清单必须同事务提交并共用 `files` 修订，使离线重置、译文生成和 Agent 原稿展开读取同一次提交的归属。

格式元数据随原稿固化，使工程可以离线重建。译文导出不写出附加原稿，使已安装的补丁在重新导出后保留。

`usage: "text"` 只表示默认翻译候选，该文本仍可能有程序依赖：

- WOLFRPG 与 RPGMAKER 的代码字符串默认排除，以保护资源名与程序协议。代价是 RGSS 的 `Vocab` 等脚本显示文本需要人工确认并放行。
- Godot 的显示文本常在脚本的字典值和数组中，因此按消费位置与文本外观选择候选。默认状态仍需结合代码依赖审校。
- 共享预过滤对原生格式只检查正文、资源引用和源语言，使人工或 Agent 放行的条目不被外观规则重新排除。

名称依赖和脚本用途由对应引擎的产品技能按实际消费代码审校，未决依赖不阻塞译文生成。

定位绑定固化原稿，使提取规则变化和条目顺序不影响写回目标。导入时的局部解析失败保留原稿，已提交译文无法应用时生成失败，避免将遗漏译文当作成功结果。

RGSS、WOLF、Godot 与 Ren’Py 的译文只提供覆盖准备后游戏目录的数据，素材由原游戏提供。

Ren’Py 的脚本发现先于游戏初始化，运行资源则使用初始化后的归档顺序。准备必须分别保留这两个阶段的有效来源。活动源码只有与编译文件摘要一致时才可移出，归档内源码保持非活动。静态加载声明无法覆盖任意 Python 动态加载行为。

Ren’Py 直接修改编译数据，以保留存档依赖的语句身份。写回必须同时处理共享引用和缓存失效。引擎可能在语法树已更新时继续执行旧缓存。

Ren’Py 译文使用基础语言。修改字符串表键时，导出需维持其他语言的映射。每次导出只在首次启动重置语言偏好，之后保留玩家选择。空字符串表也覆盖生成资源，以清除上一轮内容。

Ren’Py 译文导出与字体替换可以按任意顺序重复执行。字体不进入翻译原稿，语言初始化和字符串表归译文导出所有，断行设置归字体工具所有。准备与来源收集必须排除生成资源及其编译产物，避免重导入将其固化为原稿。

Godot 引擎优先读取包内资源，因此准备阶段将最终资源展开，让散装译文生效。载体覆盖、启动 PCK 移除、资源写入和失败恢复由同一个目录事务提交。

Godot 的覆盖顺序在只读预览后确认，并贯穿新建、追加导入与字体工具。确认期间不持有写入租约，执行前重新核对包集合。

`project.binary` 必须来自启动主载体，因为 `load_resource_pack` 不会重新加载项目设置。

附加 PCK 保留带程序标记的空载体，使原加载器继续执行加载成功后的副作用。启动 PCK 必须移走，空主包会破坏资源目录枚举。

Godot 译文导出依赖系统字体回退，实际显示取决于系统字形和控件字体，字体度量也可能混用。

Godot 字体修改保存在原稿容器外的导入映射和 `override.cfg` 中，使后续从原稿生成 `project.binary` 时仍保留字体选择。

Godot 只翻译一种 `locale` 的语言表，并让 `fallback` 指向它，以复用游戏原有的语言表加载机制。当前语言没有表时显示译文，命中其他语言表时仍显示该表原文。

游戏来源准备与工程提交分开完成，使原稿读取或后续导入失败时可以复用准备结果。

MV/MZ 明文媒体、加密配置和已消费密文的移除属于同一次来源准备。加密标志已关闭的历史双份资源保持原状，避免根据同名明文存在推断密文可以删除。

用户自行备份完整游戏目录，供成功改写后的人工恢复。界面入口在修改前等待用户确认。CLI 向 `stderr` 提示后继续执行，`stdout` 保留给机器协议。

单个游戏资产是译文导出的提交边界。游戏成员和配套资源必须一起生效，避免游戏加载不同批次的输出。后续资产失败时，保留此前成功的资产。

目录事务独占目标目录的 `.tmp/`。恢复失败时保留材料，并阻止后续写入接管。提交后的清理失败保留已提交内容，供用户继续使用。

工程写入与游戏目录占用都遵循 [占用持续到收尾](ARCHITECTURE.md#占用持续到收尾)。关闭时先取消在途操作，等准备线程退出、恢复和清理结束后再释放线程与数据库。

### PDF

PDF 按原稿页保存处置与译稿，使调查证据、修改目标和来源冲突都绑定稳定身份。输出页由排版生成，页数可以随译稿长度变化。

不同处置表达不同的工作决定：

|处置|含义|
|---|---|
|`translation: null`|尚未处理，暂时输出原页|
|`keep`|确认无需翻译，保留原页并记录理由|
|`omit`|按用户要求省略原页，并记录理由|
|空 `translate`|内容已归入其它页，本页不再输出译稿|

允许整份 PDF 无输出页，支持内容整体归并或省略。

来源字节和页级事实持久化。文字、字体和坐标提取作为可再生工作材料。

进度按原页处置统计，工程条目统计只汇总文本条目。

Agent 工作区预览用于调查与检查。预览和 `workspace_apply` 复用页面判定规则，提交时仍按最新工程事实返回逐页回执。

正式 PDF 由译文生成产出。后端在独立线程中计算，Agent 在已有 Node 子进程中调用同一文档模块，使预览与交付使用相同的排版语义。

相邻译稿在整份译文生成时连续排版，因此分页可能与单页预览不同。

## 🔎 查询与质量证据

缓存和质量评估服务于已保存的工程事实。条目、修订与缓存沿同一提交结果更新，查询恢复时可从数据库重建。

翻译、校对、规则统计与 Agent 工具共用匹配和文本准备规则，使同一术语或保护片段在各入口具有相同含义。

校对结果只表示检查发现的证据：

- 文本使用文本质量评估，PDF 使用页级处置事实。
- 没有警告不能证明译文正确。

校对窗口保留一次查询的成员与顺序，方便编辑时继续阅读：

- 正文修改后继续使用当前窗口。
- 重新查询时重新筛选和排序。
- 文件结构变化后旧窗口失效，按新范围查询。

## 🌐 模型与网络

模型管理、OneShot 与 Agent 共用能力目录和请求策略，避免同一配置在不同入口得到不同能力判断。

ChatGPT 登录只确认身份和套餐授权。模型目录与接口测试由用户独立触发，避免把临时额度和推理故障混入账户状态。

SDK 内置聊天模型提供离线基线，远端聊天目录作为可撤回的供应商覆盖。有效空目录表示撤回旧覆盖，用户模型配置独立保存。

目录联网更新保留已完成的供应商结果，并等待运行空闲后应用，保持在途配置稳定。

模型等级有两项跨入口语义：

- 思考等级属于模型全局配置，引用同一模型的入口共享该值。
- `DEFAULT` 表示沿用供应商默认，`OFF` 表示显式关闭，两者表达不同的用户选择。

### 应用代理

Electron 默认 Session 是应用代理的唯一来源。后端 HTTP、工作区 HTTP 和 Chromium 联网共用其路由，避免各网络栈分别解释配置。

- 入口先配置默认 Session，再启动后端，避免首次请求使用旧路由。
- 代理解析或连接失败会结束请求，避免静默直连改变用户的网络选择。
- 本机回环请求固定直连，保证本地模型与应用内服务可达。
- 传输层保留 HTTP 状态与重试时间，恢复决策由调用方承担。

### 公开错误

`code` 和 HTTP 状态决定恢复动作，`message` 保留具体原因供诊断。跨 API 与线程传递时保留两者，使展示措辞可以独立变化。公开原因中的凭据由接入边界处理，完整诊断保留在日志。

## 🗃️ 存储与历史工程

连接仅覆盖实际数据库批次，空闲工程应恢复为单个完整的 `.lg`，便于用户复制与移动。

工程查询、业务访问与 Agent SDK 共用串行边界，避免独立操作进入尚未结束的 SDK 事务。预览采用 `query_only` 短批次，让 SQLite 继续负责 checkpoint 与副文件收尾。

预览只提供可选信息，正式打开负责版本确认与迁移。确认等待期间释放连接与运行占用。确认绑定重新读取的工程版本，避免旧决定放行新的高版本。

应用版本在进程内固定，因此创建与迁移事务统一维护版本事实，后续业务与 SDK 写入沿用该事实。低版本打开仍保留高版本标记，避免一次确认抹去后续风险提示。保护范围限于本实例的打开流程，跨进程改写仍可能越过检查。

迁移分别处理应用文件、数据库和工程打开准备：

- 迁移标记与对应数据一起提交。
- 迁移顺序承担历史版本升级语义。
- 已停用能力的旧数据保留物理原值，当前读取只投影现行事实。

日志以正文为恢复依据，索引可以重建。外部编辑使旧游标和详情定位失效，避免读取已经错位的记录。

Agent 日志与会话恢复的关系见 [AGENT_RUNTIME](AGENT_RUNTIME.md)。
