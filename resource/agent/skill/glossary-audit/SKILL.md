# 术语表审校

以数据库事实和原文语境为唯一依据完成「发现—审校—确认—写入—复核」闭环。默认覆盖整张术语表；用户明确限定条目、词语或问题类型时严格按该范围执行。优先得到全局一致、低冗余的术语体系，不为旧条目保留无依据的兼容层。

## 审校标准

### 目标

术语表只保留会影响后续翻译一致性、属性判断或世界观理解的核心专有名词。评价结果以整张术语表的覆盖、一致性和维护成本为准，不以“尽量少改旧数据”为目标。

### 不可违反的规则

1. 先查原文实际位置和语境，再作判断；禁止按字面直觉决定译名、分类或边界。
2. `src` 必须是原文中实际出现的连续子字符串。
3. 只截取保证身份和译法所需的最小边界：
   - `骑士艾琳` → `艾琳`
   - `黑木家族的族长` → `黑木家族`
4. 本技能创建或修改条目时，`info` 只使用以下分类之一；这是审校策略，不是数据库存储硬约束：
   - `男性角色`
   - `女性角色`
   - `未知性别角色`
   - `地名`
   - `家族`
   - `组织`
   - `特殊物品`
   - `特殊技能`
   - `特殊生物`
   - `其他`
5. 不收录脱离作品设定也能直接理解的泛用词、身份、称谓或职业，例如剑、魔法、城堡、马车、怪物、公会、先生、大人、少爷、战士、商人。
6. 不用正则表达式代替精确术语边界。
7. 同一专名及其同根条目保持同一译法；有意区分时必须由语境证明。

### 每条术语的审查顺序

1. **出现事实**：确认出现次数、文件、行号、完整原文和局部位置。零出现条目不合法。
2. **语义身份**：判断它在该处指人、家族、地点、组织、物品、技能、生物还是设定概念。
3. **专有性**：判断它是否构建作品独有的世界观，或是否必须统一才能避免翻译错误。
4. **边界**：去掉爵位、称谓、职业、所属关系、泛用后缀和句法成分；保留不可拆的正式名称。
5. **译法**：结合足以覆盖不同语义的已核验语境、既有译名和同根条目选择稳定译法，修正错别字和属性错误。
6. **全局关系**：检查包含关系、共享词根、全名/简称、错拼/异体和同名异义。
7. **动作**：选择保留、修改、删除或新增；证据不足则列为未决，不擅自写入。

### 同根词全局处理

将以下情况放进同一组审查：

- 包含关系：`A` 与 `AB`
- 共享词根：`AB` 与 `AC`
- 全名、简称、称谓形式
- 地名与其派生组织、军队、领地、建筑
- 家族名与带爵位、成员全名的形式
- 技能、物品、生物名与其说明性后缀

按以下优先级处理：

1. 某条从未独立出现：删除无效条目，保留实际出现且边界正确的形式。
2. 词根即可覆盖且不会误匹配：只保留词根。
3. 派生词改变了专名身份或译法：保留必要的派生词，并统一公共词根译法。
4. 词根过短、会在普通词中误匹配：保留更精确的完整词。
5. 正式全名和简称都独立出现且译法不能由一个条目正确覆盖：两者均保留。

不要为每个“某地军”“某家领”“某人侯爵”建立补丁式条目。先决定核心实体，再用最少条目覆盖真实翻译需求。

### 语境证据要求

- 出现次数以 `query_quality_rules` 返回的 `exact_occurrences` 为准，它已覆盖全部原文。
- 完整审校要求审校范围内每条术语和关系组都有结论，不要求默认枚举每个原文命中；用户明确要求逐条检查全部语境时除外。
- 零出现条目无需查询正文。相同 `src`、`case_sensitive`、`scope` 和 `items` revision 的查询结果由相关条目共享，不重复取证。
- 先核验少量代表语境；只有语义身份、专有性、边界、译法或同根关系仍存在未决问题时，才继续读取不同语境。不得仅因查询仍有下一页而机械翻页。
- 修改译名、分类或边界时，证据至少包含一个能直接支持判断的 `item_id`。
- 删除实际出现的条目时，证据必须展示它为何是泛用词、称谓、冗余派生词或错误边界。
- 零出现条目可以用空证据列表，但理由必须明确写为未出现或被有效同根条目取代。
- 高频词按文件、完整原文和周边搭配识别代表语境；仍需覆盖已经发现的不同语义簇，并在清单中披露已核验范围与残余风险。

### 决策示例

| 原文事实 | 结论 |
| --- | --- |
| `临冬城`始终指作品内城市 | 保留为`地名` |
| `凤凰社`始终指特定团体 | 保留为`组织` |
| `剑`只表示普通武器 | 删除 |
| `骑士艾琳`中的“骑士”只是称谓 | 保留`艾琳`，删除完整称谓条目 |
| `感情伝達魔法`与`感情伝達の魔法`共享词根，`感情伝達`可正确覆盖 | 只保留`感情伝達` |
| 同一字符串在不同位置分别指人名和地名 | 不凭字符串强行合并；若单条替换无法安全表达，列为未决并说明工具限制 |

### 变更清单质量门槛

每项变更必须能回答：

- 完整出现次数是多少，哪些已核验原文位置能直接支撑结论？
- 在这些位置具体指什么？
- 为什么它是术语或不是术语？
- 为什么边界是必要的最小范围？
- 它与同根条目的关系是什么？
- 修改后能否用更少条目保持覆盖？
- 译法和分类是否与全表一致？

回答不全时，不进入可执行计划。

## 工作流

### 1. 建立事实快照与审校范围

本轮审校开始时调用一次 `query_quality_rules` 并指定 `rule_type: glossary`，读取完整术语表、每条的 `exact_occurrences` 与 `fact_violations`、`structure` 的 `duplicate_src_groups` / `containment_candidates` / `root_candidates` 三组，以及 `sectionRevisions`。

- 用户未限定范围时，审校全部条目。
- 用户明确限定范围时，只为范围内条目形成结论和变更；直接相关的范围外条目可以作为关系证据，但不得擅自纳入变更。
- 零出现、空译文、正则、重复、包含和共享词根只是排序审校队列的事实信号，不能据此跳过没有信号的范围内条目。

### 2. 建立关系组并逐项审校

先按重复、包含和共享词根关系把范围内条目组成审校组，其余条目单独成组；关系证据必须在同组内共同判断，避免同根条目各自得出冲突结论。范围内每条术语最终都必须得到保留、修改、删除或未决结论。

按上述七步审查顺序逐项决定保留、修改或删除；审校组内按同根词 5 优先级先定整体结构再定单项结果。用户限定范围时，涉及范围外条目的冲突只列为未决，不擅自扩大变更。任何无法由出处证明的判断同样列为未决。

### 3. 按需读取原文证据

- 零出现条目不查询正文；以完整出现次数和关系事实作为证据。
- 按 `case_sensitive` 分组，用 `query_project_items` 的 `search` 模式、`scope: src` 和去重后的 `patterns` 查询；首次查询显式使用 `limit: 20`。
- 按上述语境证据要求决定是否继续使用 `cursor`；每次继续前先明确尚待解决的问题，问题解决后立即停止。

### 4. 生成变更方案

逐项列出每个 create / update / delete，必须包含：

- 目标 `entry_id`（create 除外）；
- 新增或修改后的完整条目（`src` / `dst` / `info` / `case_sensitive`）；
- 每项支撑判断的 `item_id` 证据（零出现条目可用空证据，理由须明确写为未出现或被有效同根条目取代）；
- 非空语义理由与同根处理说明。

方案只表达与原快照的差异，不重写未变条目，不夹带格式整理。

### 5. 先交付变更清单并等待明确批准

向用户交付：新增 / 修改 / 删除清单、每项的出处与语义理由、同根处理、保留项中的重要歧义、变更前后数量，并明确声明尚未写入。

到此停止，等待用户对当前方案的明确批准。不得把「继续」「看起来可以」等模糊表达解释为授权。若用户修改方案，重新展示完整变更清单并再次等待明确批准。

### 6. 批准后原子写入并复核

获得明确批准后调用一次 `update_quality_rules`，指定 `rule_type: glossary`，提交完整 changes 和 `expected_section_revisions: { quality: sectionRevisions.quality }`。

- 出现 `RevisionConflictError` 时不得覆盖或强写：重新 `query_quality_rules`，按原审校范围基于新快照生成新方案，回到第 5 步再次等待批准。
- 写入成功后直接以 `update_quality_rules` 的返回结果复核，不追加重复查询；向用户报告新 revision、变更及最终数量、以及未执行或未决项，只报告已确认事实。
