# 质量规则工作流

本技能是质量规则任务的唯一入口与流程权威。它把当前工程事实、既有质量规则和探查过程中发现的规则需求放入同一个自启发闭环，目标是构造当前业务范围内充分、正确、安全、一致且维护成本合理的规则集合。

领域技能提供对象资格、字段和安全表达判据；工作区工具及 `workspace.contract` 提供数据、查询、变更记录与提交行为的权威定义。

## 工作流总览

按以下顺序执行；第 4 步是循环，第 5 步负责确认循环是否真正耗尽：

1. **确定范围**：固定调查范围、调整范围、规则类型和排除项。调查范围决定检查什么，调整范围决定最终允许形成哪些业务结果。
2. **建立初始种子**：综合随机采样、既有规则和用户范围选择发现方向；至少有一个方向不依赖既有规则。采样只选择初始方向，不能裁剪声明范围的完整扫描。
3. **初始化事实**：加载当前工作区快照以及 `items`、`sources`，形成可探查的初始发现前沿。
4. **执行发现与核验循环**：完整执行当前前沿中的可执行探查，登记对象、关系、边界、分支和变化；完整消费结构分组、分页与跨组关系；逐对象形成结论；再让工程事实与既有规则双向反馈，记录新增对象、变化对象和后继探查，形成下一轮发现前沿。
5. **确认发现是否耗尽**：当前前沿达到零增量后，使用不同于既有探查依据和方法的独立方向建立新种子。独立方向产生增量时回到第 4 步；独立方向也保持零增量时，才确认发现前沿耗尽。
6. **构造并验收目标集合**：形成目标规则集合，执行程序化收敛验收；存在缺口时继续补查，只有零缺口才准备变更。
7. **授权后最终化**：获得明确授权后，只通过 `workspace_apply` 写入，重新加载最新快照，并返回真实回执与业务报告。

后续章节分别定义上述阶段的事实、判据、账本、工具调用和恢复规则；本节只保留执行顺序与不可跳过的收敛边界。

## 1. 确定范围与任务目标

质量规则任务默认同时完成两项工作：

1. 从工程事实发现尚未形成规则的对象和结构；
2. 结合完整证据核验当前范围内的既有规则，并把核验结果反馈给整体规则集合。

用户明确的规则类型、目标、文件范围和排除项直接形成调查范围与调整范围：

| 用户表达 | 处理范围 |
|---|---|
| 未限定规则类型 | glossary 与 text_preserve |
| 指定术语、名称、译名或实体 | glossary |
| 指定控制符、占位符、格式结构或文本保护 | text_preserve |
| 指定只新增、只核验或只处理某组规则 | 按用户要求收窄调查范围或可写入的业务结果 |

调查范围决定参与发现、证据核验和关系分析的工程事实；调整范围决定哪些最终业务结果可以形成写入方案。既有规则会参与完整理解，即使当前调整范围只允许新增或只允许处理指定对象。

范围包含 glossary 时读取 `@skill(glossary-rules)`；包含 text_preserve 时读取 `@skill(text-preserve-rules)`。pre_replacement、post_replacement 和 item 修改属于范围外对象，只在当前事实直接关联且有助于说明边界时作附带观察。

## 2. 技能工作资产与收敛协议

本技能的机械状态只保存在当前工作区的两个文件中；它们是可重建的流程资产，消费边界限定在本技能的工作流内：

```text
scratch/quality-rule-scope.json
scratch/quality-rule-ledger.jsonl
```

`scope` 固定本次调查和允许写入的边界：`mode` 为 `create`、`review` 或 `maintain`，并记录 `kinds`、`allowed_actions`、`target_entry_ids`（`null` 表示未按既有规则 ID 限定）和 `existing_entry_policy`（`all`、`listed` 或 `evidence_only`）。`review` 默认使用 `all`，创建任务默认使用 `evidence_only`；需要改变默认值时必须显式写入，不能由验收脚本猜测用户意图。

`ledger` 每行用 `type` 的 `check` 或 `target` 区分记录。`check` 表示一项可以完整执行的发现或补证工作；结构字段由本轮验收脚本从轮次和方法派生，模型只填写本轮事实：

```text
{ type: "check", origin: initial | triggered | independent, round,
  kinds, scope, method, independent_of_existing_rules,
  status: pending | complete,
  counts: { raw_matches, consumed, rejected },
  targets: { new, changed },
  spawned: [ { kinds, scope, method } ] }
```

`raw_matches = consumed + rejected`；`complete` 只表示声明范围已完整执行、没有截断且所有分页已消费。`initial` 至少有一项将 `independent_of_existing_rules` 设为 `true`；`triggered` 必须由上一轮的 `spawned` 描述产生；`independent` 不得由其它方向产生，并且其 `kinds`、`scope`、`method` 组合不得与已有方向重复。探查记录的标识、增量和父子索引由本轮验收脚本派生，不再写入账本。

`target` 每行表示一个需要独立决定的业务对象：

```text
{ type: "target", key, kind, origin: candidate | existing, id?, evidence, decision }
```

对象由 `check.targets.new` 或 `check.targets.changed` 单向登记来源；本轮验收脚本负责反向覆盖校验。`decision.necessity` 使用 `required`、`not_required` 或 `unknown`，`decision.resolution` 使用 `direct`、`conditional`、`narrowed`、`preserved` 或 `blocked`。`origin` 为 `candidate` 时，`decision.action` 只允许 `create`、`discard` 或 `blocked`；`origin` 为 `existing` 时，只允许 `keep`、`update`、`delete` 或 `blocked`。判断为必须收录的业务对象必须由安全规则覆盖，或在所有降级路径耗尽后单独记录未决原因和解除方式。

账本更新使用现有 `workspace_script` 的 `writeJson` / `writeJsonl`，每轮以一次文件事务同时提交结果和后继状态。`task_progress` 只用于导航、恢复和防遗忘，不参与收敛证明；任何“已完成”文字都不能代替账本状态。

采样只负责选择初始方向。一旦形成可执行模式，必须扫描声明范围；频率、长度、Top-N、已有译文、已有规则覆盖、证据难度和预计动作只能影响排序、上下文预算和报告方式，不得影响扫描范围、对象登记或最终判断。

## 3. 建立规则对象与目标集合

当前任务维护规则理解集合，集合成员来自三类事实：

- 当前范围内的既有规则；
- 工程事实中直接观察到的规则需求；
- 探查既有规则或新需求时生成的关联对象、关系和边界形态。

每个有效唯一对象先登记，再应用领域判据。登记保留完整发现来源、重复身份、命中、语境、关系和补查记录；对象当前是否已有规则只影响最终业务处置，不影响它进入发现和核验集合。

最终目标是把当前范围内全部对象构造为一个目标规则集合，再将当前规则集合与目标集合进行业务比较。比较结果可以形成新增、保留、调整、移除或未决方案；工作区中的技术记录只承载这些方案的可执行差异。

## 4. 自启发种子与发现前沿

初始种子由以下内容共同组成：

- 不同文件、章节或结构层的随机采样片段；
- 当前范围内的既有规则及其代表命中；
- 用户声明的范围、规则类型和排除项。

随机采样用于打开互补的发现方向，既有规则用于提供已有术语、保护结构、覆盖关系和边界样本。种子帮助选择第一轮探查前沿；可由程序完整执行的模式一旦出现，就在声明范围内完成完整探查。

基础发现方向至少覆盖：

- glossary：完整名称边界、身份与别名、首次出现和身份变化、命名或定义槽位、并列或同构结构、译法分歧、原文残留、文件长尾和单次概念；
- text_preserve：控制符、占位符、格式脚手架、相关 warning、已有译文中的结构损坏和保护边界。

基础方向至少有一个不依赖既有规则；其它方向由采样和既有规则共同启发。每个方向都带有明确的范围与方法，能够交给 `workspace_script`、`workspace.matchLiterals` 或其它工作区查询完整执行。

## 5. 自启发循环

自启发循环是任务的主流程。每一轮同时探查当前发现前沿并生成下一轮前沿：

循环基于当前批次的完整只读快照执行，快照包含空的工作区变更记录和当前对话的 `task/**`；同一批次的对象、证据、探查和方案都基于这份快照形成。items 是默认事实来源，items 缺少片段、顺序、层级或容器结构时，再依据 `project_meta` 的映射定点读取 `sources/**`。

确定性匹配、计数、结构关系和完整范围使用工作区查询；大数据使用 `workspace_script` 的 `iterateJsonl` / `writeJsonl` 流式处理。工作区脚本读取只读快照和 sources，并通过 contract 声明的固定工作区变更记录、`task/**` 与 `scratch/**` 保存结果。

1. 从当前快照读取尚未执行的模式、受影响对象和具体补查；
2. 将可等价合并的探查合并为一次或少数几次完整扫描；
3. 使用工作区查询完成确定性匹配、计数、结构关系和完整范围处理；大数据通过 `workspace_script` 流式处理；
4. 从探查结果提炼新对象、新关系、新边界、新分支和新的可执行模式；
5. 重新核验受到影响的既有规则和潜在规则需求；
6. 把尚未执行的新模式与受影响对象加入下一轮；
7. 记录本轮新增对象、变化结论、补查和扫描完整性。

任务规模、提交规模和模型上下文规模分别管理。程序可以确定处理结果的内容先在完整声明范围内完成；需要开放式判断的对象按领域单元、自然业务分组和稳定顺序安排上下文。工作项记录发现前沿、独立方向、提交批次或最终化阶段，不以单个程序化对象建立工作项。

长任务在开始时使用公共 `task_progress` 建立粗粒度工作队列，覆盖初始种子、发现前沿、独立方向和最终化阶段，工作项表示需要继续处理的批次或阶段。每项取得真实结果后推进，并在同一次更新中追加由结果产生的后继工作。恢复、上下文压缩或进度不明时先读取现有进度；领域验收和最终化完成后再结束工作队列。

每个新模式都要具备可完整执行的范围和方法。已有证据能够回答的问题直接复用已有结果；等价方法通过内容归并而不是改名重复执行。暂时缺少可执行探查方法时，将该信息保留为当前对象的语境证据或未决说明。

每轮的程序化扫描覆盖声明范围，完整处理可以定位的对象；频率、长度、Top-N、已有译文、已有规则覆盖、证据难度和预计动作用于排序、结果分析和报告，不参与范围裁剪、对象登记或最终判断。完整中间结果写入当前快照的 `scratch/**`，向模型返回计数、变化对象和少量代表证据。

## 6. 双向反馈增强

双向反馈是自启发循环的增强机制。它让工程事实与既有规则互相生成下一轮发现方向：

| 反馈方向 | 探查起点 | 形成的下一轮发现 |
|---|---|---|
| 工程事实 → 规则集合 | 文本、结构、语境、格式形态和译文痕迹 | 尚未覆盖的对象、别名、分支、变体、保护结构和边界例外 |
| 规则集合 → 工程事实 | 规则命中、覆盖范围、重复关系、冲突、异常和替代表达 | 漏覆盖对象、过宽边界、可拆分形态、同类结构和需要补证的语境 |

新发现的对象会回到既有规则核验；既有规则暴露的边界会回到工程事实探查。两条方向产生的结果进入同一个发现前沿，并共同推动相关集合重新分组和重新判断。

双向反馈同时适用于 glossary 与 text_preserve：两类对象共用每轮 items 遍历、上下文片段和发现范围，分别应用各自领域判据，最终分别形成安全规则集合后再汇总任务结果。

## 7. 结构关系与完整消费

对象登记后、模型逐项判断前，按规则类型调用 `workspace.groupQualityRuleEntries(...)`。已有规则与新发现使用相同的 `{ entry_id, src, case_sensitive? }` 投影格式，使结构算法能够按共同顺序核验同一业务集合。

- 按 `next_offset` 持续读取全部分页；每个返回组最多 16 个对象；
- 超大强 component 拆组时保留共同 `component_ids`，并把每页 `cross_group_relations` 反馈给相关对象和具体补查；
- `equivalent`、`contains`、`shared_root`、component 与相邻结构表示共同核验原因，语义身份、必要性和最终合并仍由对象证据独立决定；
- 所有目标组按稳定顺序消费，每个对象形成独立结论；结构组数、component 数和公共字面数用于说明探查关系，业务对象数量和语义合并数量依据对象结论统计。

glossary 在语境确认明确子集属于同一业务对象或规则体系后，调用 `workspace.deriveCommonLiteralRoots({ forms })` 枚举公共连续片段，再用 `workspace.matchLiterals` 比较拟替代分支的完整命中。新增命中逐项归入遗漏成员或边界反例，并把结果反馈到下一轮；公共片段的安全性不足时，保留已经验证安全的精确分支。

text_preserve 的正则源码按执行语义独立判断。完全相同的源码可以作为共同核验对象；每条规则仍依据自己的真实命中、保护边界和结构位置形成结论。

## 8. 对象判定与领域表达

每个对象依次完成以下判断：

1. 当前工程事实是否支持由本领域处理；
2. 需要保护或稳定表达的范围是什么；
3. 直接规则、条件规则、收窄边界或拆分分支中哪种表达最安全；
4. 它与其它对象之间的覆盖、重复、冲突、别名、同一体系或边界关系如何影响目标集合；
5. 缺失的决定性事实是什么，下一轮可以如何取得。

表达路径按以下优先级逐级收敛：

- 直接使用：规则对全部适用输入保持安全；
- 按输入语境使用：翻译输入能够判断适用条件，`info` 同时说明采用条件与其它语境的处理原则；
- 收窄边界：缩小连续字面或正则范围，隔离确定安全的部分；
- 拆分分支：把不同实体、别名、格式结构或行为分成独立规则；
- 未决：完整补查和上述表达路径仍缺少决定性事实时，记录缺口、已完成调查、失败原因和解除方式。

glossary 依次判断收录资格、译名正确性、充分性、作品风格、一致性和集合最小性。text_preserve 依次判断保护必要性、表达式有效性、真实匹配、安全边界、覆盖充分性和集合最小性。集合优化以已经确认的对象资格和安全表达为基础。

既有规则初始化时取得正式命中、文件分布、文本类型和必要语境。glossary 使用 `workspace.matchLiterals` 批量取得 `src` / `name_src` 的完整命中；text_preserve 在 items 遍历中累计真实命中、分布和代表证据。范围明确指定既有规则时，可以使用 `target_entry_ids` 约束本轮重点对象，相关范围外成员继续作为结构、覆盖和边界证据参与判断。

零命中表示当前快照没有适用证据。既有规则在缺少直接调整依据时延续原值；非法表达式、零长度命中、领域资格消失、被目标集合完整覆盖或其它直接事实可以形成调整依据。零命中本身保留为证据，不单独生成调整结论。

## 9. 发现前沿耗尽与独立方向

自启发循环持续到当前发现前沿耗尽：

- 初始种子已经完成探查；
- 每个新模式的完整范围探查已经完成；
- 新对象、边界例外、关系变化和替代表达已经回流并重新核验；
- 最近完整一轮保持对象、结论和补查集合稳定。

当关联前沿达到零增量后，使用不同于既有探查依据的独立方向建立新的发现种子。独立方向可以从文件长尾、章节结构、低频形态、命中残差、边界反例、覆盖缺口或替代分支进入。独立方向的所有结果重新回到同一自启发循环；它产生增量时继续下一轮，未产生增量时完成发现穷尽核验。

“发现穷尽”指声明范围内所有已知和自启发产生的可执行发现方向均已消费，完成结论的适用边界限定在当前声明范围。

glossary 范围中的同一实体、别名、所属、同一体系、派生形式、异义实体和覆盖关系，在当前语境确认后作为相关对象的证据和关系图内容保留，用于作品理解、规则背景、合并、拆分和消歧；关系暴露的新身份、别名、边界反例或决定性事实时，立即形成下一轮探查。

闭环判例：

| 探查结果 | 下一轮动作 |
|---|---|
| 公共字面覆盖比分支集合多出条目 | 完整扫描新增条目，分别判断遗漏成员和边界反例 |
| 一个名称暴露同一槽位的其它字面量 | 扫描该槽位，登记新的唯一身份并重新分组 |
| 宽占位符同时命中结构与正文 | 按定界符、位置或结构形成更窄模式并完整复核 |
| 既有规则出现覆盖缺口或过宽命中 | 回到工程事实寻找同类形态，并重新评价相关规则集合 |
| 一轮没有产生增量 | 消费独立方向种子；独立方向也零增量时完成发现穷尽核验 |

## 10. 目标规则集合与程序化验收

目标集合完成后，必须由 AGENT 为当前任务编写一次性 `workspace_script` 并执行。脚本只消费精简账本、当前质量规则数据集和 `workspace.contract`；不把脚本保存为技能资产，也不得把模型自己口头宣布完成当作验收结果。

验收脚本必须检查以下不可删减的不变量：

- `scope`、规则类型、既有规则策略和允许的 `action` 合法且未越界；
- 方法签名、轮次、分页完整性、`pending` 状态和 `raw_matches = consumed + rejected` 对账；脚本自行派生探查记录标识、增量和父子索引；
- `spawned` 描述的后继方向在下一轮存在，每项探查声明的对象均已登记，且每个业务对象至少有一项已完成的来源探查；
- 初始方向至少有一个不依赖既有规则，最后一轮包含 independent 且整轮零增量；第 0 轮不能直接完成；
- 每个业务对象都有合法、完整的处置结论；判断为必须收录的对象有规则覆盖，或单独记录未决原因与解除方式；
- 既有规则覆盖策略、目标对象集合、规则字段和 `create`、`update`、`delete` 变更之间可对账；`move` 永远为空；
- 其它规则类型、items、prompts 和范围外变更没有被带入本次方案。

存在缺口时，脚本只返回按 `code` 分组的缺口数量、少量对象示例和业务统计，不写任何变更记录。零缺口时，脚本才在同一事务中整体生成选定规则类型的 `create`、`update`、`delete` 文件并清空 `move` 文件，然后返回 `changes_prepared`。生成后只要账本、验收脚本或变更记录再被修改，就必须重新执行脚本。

这是一项技能内的标准化、自律式验收，强制范围等同于 Agent 对本技能协议的遵循程度；宿主仍保留独立的 `workspace_apply` 调用路径。因此对外表述为“已按技能协议完成审计”，并把审计适用范围限定在当前技能任务。

## 11. 授权、写入与快照生命周期

未获授权时形成具体业务方案，工作区只保存待提交的技术记录。获得明确授权后，依据 `workspace.contract` 生成完整、可对账的工作区变更，并只通过 `workspace_apply` 写入；方案中的业务对象、规则类型和调整范围保持与授权一致。

请求写入授权前，使用用户语言按业务原因说明：

1. 规则类型、调查范围、调整范围、排除项和范围完整性；
2. 发现与核验对象总量，以及新增、保留、调整、移除、无需收录和未决数量；
3. 当前规则数量与目标规则数量，以及初始种子、关联探查、双向反馈和独立方向的完成情况；
4. 各类业务处置的代表示例，使用分类说明承载共同标准；
5. 代表证据、合并、拆分、覆盖关系、例外、未决解除方式和范围外观察；
6. 当前范围的实体关系图，以及图中各实体和关系的核验状态；
7. 写入范围、实际影响和需要用户确认的授权内容。

当前范围产生真实业务差异时，请求对应授权；没有真实差异时，说明无需授权并保持工作区变更记录为空。授权覆盖范围、标准和例外在后续提交批次中持续有效，直到用户调整方案、事实快照发生冲突或出现标准尚未覆盖的新形态。

每个提交批次以一次无参数 `workspace_load` 开始，遵循完整的“加载—探查—反馈—独立方向—集合验收—授权—apply—回执”周期；等待授权仍属于当前批次。`workspace_apply` 成功或确认无变化后当前快照失效，后续工作从新的 `workspace_load` 开始。

工作区提交成功或确认无变化后，后续工作重新加载最新事实；stale、revision 冲突和提交回滚依照工作区返回的恢复动作重新计算受影响方案。已提交但同步失败时报告真实写入状态并等待工程重新加载。

当前快照可重建的中间结果放入 `scratch/**`；跨快照仍需保留的未决事项、范围决定或授权信息放入 `task/**`。

## 12. 面向用户的业务结果

内部逐项闭合保证范围完整；对外回复提供面向决策的业务摘要。默认报告包含：

1. 业务范围、规则类型、排除项和范围完整性；
2. 发现与核验对象总量，以及新增、保留、调整、移除、无需收录和未决的分类数量；
3. 当前规则数量与目标规则数量；
4. 按业务原因归组的共同处理原则；
5. 每类少量代表证据；
6. 会改变用户判断的例外、关系、未决和解除方式；
7. 实体关系图；
8. 写入范围、授权状态、影响和真实回执。

完整条目清单、逐条结论或机器可读结果在用户明确要求时展开；普通保留项和同类确定性结果以汇总与代表证据表达。

用户可见内容使用业务语言，说明规则对象、实际影响和处理结果。工作区字段、内部身份、操作名称、临时资产、工作项、轮次、组标识和工具载荷留在执行层；技术结果先转换为用户可理解的新增、保留、调整、移除或待补证业务表达。

实体关系图用于帮助用户理解作品中的实体、别名、所属、同一体系、派生关系和异义边界，并在形成新身份、别名或边界事实时回到自启发循环，绘图时按信息密度选择以下形式：
- 关系少且结构清楚时展示一张完整 Mermaid 关系图；
- 存在多个语义簇时展示簇级总览，并为影响合并、拆分或消歧的簇补充局部图；
- 关系过密时展示主要实体主干，并用关系表保留必要的图外关系。
- 每张图控制在 8 至 12 个节点，超出时拆分或降级展示；

完成表示声明范围、初始种子、双向发现前沿、独立方向和目标集合均已收敛；完成结论适用于当前范围，理论规则空间的其它可能性保留为范围外空间。
