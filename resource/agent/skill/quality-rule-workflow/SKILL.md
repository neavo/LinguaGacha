# 质量规则工作流

本技能是质量规则任务的流程权威。它负责把用户范围、工程事实、既有规则和领域技能判断组织成一个可追溯、可收敛的任务；glossary 与 text_preserve 的对象资格、字段和安全表达分别以对应领域技能为准。

工作流以**自启发循环**为核心：每轮完整消费当前发现前沿，根据结果生成下一轮对象、关系、边界和探查方向，直到关联前沿与独立方向都没有增量。

## 默认执行语义

用户调用本技能后，默认围绕用户指定的对象或范围，完成既有规则审校、工程事实发现、自启发循环、目标规则集合构造与验收，以及后续调整方案准备。任务结果形态遵循用户目标：信息结果形成审查或方案，工程变更结果形成并提交 change。用户明确限定阶段、规则类型、范围或结果形式时，按其限定执行。

质量规则的对象关系、覆盖和集合最小性需要在完整范围内共同验收，因此工程变更结果采用完整范围原子性：全部业务单元完成后形成一个提交批次。调用 `workspace_apply` 前完成审校、发现、验收和方案准备；工具返回结果后继续验证和报告。

## 1. 任务范围与领域路由

先固定本次调查范围、可形成的业务结果、规则类型和排除项。调查范围决定检查哪些工程事实，调整范围决定方案拥有的结果；范围外规则只提供结构、覆盖或边界证据。

| 用户表达 | 领域范围 |
|---|---|
| 未限定规则类型 | glossary 与 text_preserve |
| 指定术语、名称、译名或实体 | glossary |
| 指定控制符、占位符、格式结构或文本保护 | text_preserve |
| 指定只新增、只核验或指定规则 | 按用户要求收窄调查范围或允许的 action |

范围包含 glossary 时读取 `@skill(glossary-rules)`；包含 text_preserve 时读取 `@skill(text-preserve-rules)`。领域技能独占各自的发现方向和对象判据，workflow 负责组织共同流程。

`scope` 至少记录：

- `result`: `report` 或 `change`；
- `mode`: `create`、`review` 或 `maintain`；
- `kinds`；
- `allowed_actions`；
- `target_entry_ids`，`null` 表示不按既有 ID 限定；
- `existing_entry_policy`: `all`、`listed` 或 `evidence_only`。

默认策略必须显式写入：`review` 默认 `all`，`create` 默认 `evidence_only`；`maintain` 依目标 ID 决定，未指定 ID 时为 `all`，指定 ID 时为 `listed`。用户要求优先于这些默认值。

## 2. 工作资产

质量任务基于一个当前事实快照形成完整目标规则集合；items 是默认事实来源，缺少片段、顺序、层级或容器结构时依据 `project_meta` 定点读取 sources。

`task/**` 保存跨快照仍有效的范围、决定、未决和恢复摘要；`scratch/**` 保存可从最新快照重建的账本、探查结果、覆盖核验、临时目标集合和待提交 change。写入策略由 Agent 会话运行态持有，不写入 task 或 scratch。新快照复用仍有效的 task 决定并重新计算过程资产。

本技能的账本承担发现穷尽和目标覆盖证明，通过 `workspace.writeJson` / `writeJsonl` 以文件事务写入；`task_progress` 承担导航、恢复和防遗忘。

## 3. 账本对象

账本至少包含 `check`、`target` 和 `proposal` 三类记录。

探查记录：

```text
{ type: "check", origin: initial | triggered | independent, round,
  kinds, scope, method, independent_of_existing_rules,
  status: pending | complete,
  counts: { raw_matches, consumed, rejected },
  targets: { new, changed },
  spawned: [ { kinds, scope, method } ] }
```

`raw_matches = consumed + rejected`。`complete` 表示声明范围完整执行且所有分页均已消费。`triggered` 由上一轮的 `spawned` 产生；`independent` 由新的独立种子产生，其 `kinds`、`scope`、`method` 组合与已有方向不同。

对象记录：

```text
{ type: "target", key, kind, origin: candidate | existing, id?, evidence,
  decision: { necessity, resolution, action, covered_by: [proposal_key] } }
```

`decision.necessity` 使用 `required`、`not_required` 或 `unknown`；`decision.resolution` 使用 `direct`、`conditional`、`narrowed`、`split` 或 `blocked`。`conditional` 只适用于 glossary。候选对象的 `action` 为 `create`、`discard` 或 `blocked`；既有对象的 `action` 为 `keep`、`update`、`delete` 或 `blocked`。

判断为 `required` 的对象必须填写 `covered_by`，指向一个或多个最终规则方案；无法安全覆盖时，必须使用 `blocked` 记录缺口、已完成调查和解除方式。

规则方案记录用于覆盖闭合和最终集合对账：

```text
{ type: "proposal", key, kind, fields,
  covers: [target_key],
  matches: { base, additional, conditional, rejected },
  status: candidate | selected | rejected }
```

方案使用任务内稳定键表达当前技术记录；正式写入通过 contract 声明的 change 文件提交。

## 4. 初始种子

初始种子由以下来源共同选择：

- 不同文件、章节或结构层的互补采样；
- 当前范围内既有规则及代表证据；
- 用户声明的范围、规则类型和排除项；
- 领域技能规定的基础发现方向。

采样用于选择第一批方向；声明范围的完整扫描与账本消费状态承担完整性证明。初始方向至少有一项不依赖既有规则，并在账本中明确标记 `independent_of_existing_rules: true`。

## 5. 自启发循环

自启发循环按“当前前沿—探查结果—后继前沿”持续推进。

每轮必须按以下逻辑运行：

1. 从当前快照读取尚未执行的方向、受影响对象和具体补查；
2. 将内容等价且范围、方法相同的探查合并，避免重复扫描；
3. 使用工作区查询完整消费声明范围，记录计数、分页和代表证据；
4. 登记新对象、新关系、新边界、新分支和新证据；
5. 重新核验受影响的既有规则和潜在规则需求；
6. 把每个新模式和后继方向写入下一轮发现前沿；
7. 提交本轮结果，并保留来源、变化和完整性记录。

每个后继方向必须能回答“由上一轮什么结果启发、要补查什么、使用什么范围与方法”。

以下结果必须回流下一轮：新对象、别名、变体、同名异义、覆盖缺口、过宽边界、边界反例、替代表达、关系变化和决定性事实。

每轮都要同时进行双向反馈：工程事实生成未覆盖对象、别名、分支和边界例外；既有规则的命中、覆盖缺口、重复、冲突和过宽边界反过来生成新的工程探查方向。

增量包括新对象，以及对象结论、关系、边界、覆盖集合、未决集合或补查方向的变化。任一项发生变化时，当前前沿保持活动状态。

当关联发现前沿没有增量时，必须使用与已有依据不同的独立方向建立新种子。独立方向产生增量时回到普通循环；独立方向也保持零增量时，才允许进入发现穷尽核验。

### 自启发循环判例

以下判例是本协议的规范性投影，用于说明探查结果如何转移流程状态；领域技能负责对象资格和规则表达判断。

|本轮事实|必须动作|状态变化|
|---|---|---|
|初始方向完成，并发现新对象|登记对象，生成带来源的 `triggered` 方向|下一轮前沿进入 `pending`|
|既有规则暴露覆盖缺口、过宽边界或边界反例|回到工程事实补查，并重新核验受影响对象|生成新的关联前沿|
|探查结果产生新关系或决定性事实|登记关系及其来源，重新核验相关对象|关系变化回流下一轮|
|本轮没有新对象，但对象结论、关系、边界或补查集合发生变化|继续消费受影响方向并记录增量|当前前沿保持活动|
|关联前沿完整消费且保持稳定|使用不同依据启动 `independent` 方向|进入独立穷尽核验|
|独立方向发现新对象或新边界|登记结果并回到关联自启发循环|流程转回关联前沿|
|独立方向完整消费且没有增量|进入发现穷尽核验和目标集合阶段|发现阶段才允许结束|

## 6. 发现穷尽条件

只有同时满足以下条件，才能结束自启发循环：

- 初始方向已完整消费；
- 每个后继方向已完整消费；
- 新对象、关系、边界和替代表达已回流并重新核验；
- 最近完整一轮对象、结论和补查集合稳定；
- 至少执行过一个独立方向；
- 独立方向完整消费且没有增量。

完成判定要求 `round > 0`。

“发现穷尽”的适用边界是当前声明范围内已知和自启发产生的全部可执行方向。

## 7. 结构关系与领域判断

对象登记后、逐项判断前，按规则类型调用 `workspace.groupQualityRuleEntries(...)`。结构关系用于安排共同核验、暴露覆盖或边界线索；语义身份、必要性和最终合并由领域证据独立确定。

- 按 `next_offset` 消费全部分页；每组最多 16 个对象；
- 拆分超大 component 时保留 `component_ids`，并把 `cross_group_relations` 回流相关对象；
- `equivalent`、`contains`、`shared_root` 和相邻关系表示共同核验原因；
- 每个业务对象仍须形成独立结论。

领域技能解释 glossary 公共词根和 text_preserve 相同正则源码的领域语义；workflow 负责安排相关核验与回流。

## 8. 目标集合与覆盖闭合

发现穷尽后，先由领域技能形成目标规则集合，再进行程序化验收。

验收必须同时检查：

- 范围、规则类型、既有规则策略和 action 合法且未越界；
- 所有探查分页、轮次、`pending` 状态和计数可对账；
- 每个后继方向均由上一轮产生；
- 每个对象至少有一项已完成的来源探查；
- 每个业务对象都有合法、完整的处置结论；
- 每个 `required` 对象都有 `covered_by`，或有完整 `blocked` 说明；
- glossary 方案覆盖没有遗漏对象，所有额外命中均已归入 `additional`、`conditional` 或 `rejected`；
- 既有规则、目标集合、字段和 change 之间可对账；
- 其它规则类型、items、prompts 和范围外变更没有被带入方案。

text_preserve 以单条规则为验收单位，逐条验收资格、表达式和已知命中安全。

存在缺口时返回缺口和代表证据。零缺口时，`report` 形成完整目标规则方案，`change` 准备选定规则类型的 create、update、delete、move 文件；具体 change 操作由目标集合和 contract 共同确定。

## 9. 写入与恢复

质量领域在当前事实快照上完成自启发循环和目标集合验收。`report` 核对并报告目标规则方案；`change` 把验收通过的完整目标规则集合形成一个提交批次，并调用一次 `workspace_apply` 取得真实回执。

提交前用户调整方案、事实快照冲突、stale、revision 冲突或出现新形态时，按工作区返回的恢复动作重新读取并形成完整目标规则集合。已提交同步失败时报告真实写入状态并执行恢复动作。

## 10. 面向用户的结果

报告使用业务语言，至少说明：

- 范围、规则类型、排除项和完整性；
- 对象总量及新增、保留、调整、移除、无需处理和未决分类；
- 当前规则与目标规则数量；
- 自启发循环和独立方向是否收敛；
- 共同处理原则、代表证据、覆盖关系、例外和未决解除方式；
- 实体关系图；
- `change` 结果的写入策略、写入范围、实际影响和真实回执。

### 实体关系图

实体关系图用于帮助用户理解作品，图可呈现：
- 实体、别名和同名异义边界；
- 所属关系、同一体系和派生关系；
- 影响规则合并、拆分、译名或消歧的其它已核验关系。

使用译文语言绘图，并按信息密度选择形式：
- 关系少且结构清楚时展示一张完整 Mermaid 关系图；
- 存在多个语义簇时展示簇级总览，并为影响合并、拆分或消歧的簇补充局部图；
- 关系过密时展示主要实体主干，并用关系表保留必要的图外关系；
- 每张图控制在 8 至 12 个节点，超出时拆分或降级展示。

编纂实体关系图时新发现的实体、别名或边界关系回到自启发循环，重新核验相关对象后更新关系图。
