# 译文审查

在当前工程内完成条目译文审查与修复：确认范围 → 读取候选 → 本层审查 → 方案确认 → 原子写入 → 结果核对。

## 目标与边界

- 本技能只写条目的正文译文（`dst`）、姓名译文（`name_dst`）或人工状态（`status`）。
- 警告是候选入口，不自动等于错误，也不自动等于可忽略。
- 用户明确选择尚无译文的条目时，可以形成新增译文方案。
- 每个候选必须得到且只能得到一项处置；自动修复只写入符合已批准规则的确定性差异。

## 范围模型

审查范围由两个维度共同决定：

1. **状态范围**：默认“翻译成功（PROCESSED）”。
2. **候选来源**：默认“存在警告的条目”，也可选择全部条目或明确条目 ID。

用户还可以指定警告类型、文件或文本条件。

确认规则：

- 两项都未明确时，一次询问两项。
- 只明确一项时，只询问缺失项。
- 两项均明确时，不重复询问。
- “默认即可”确认默认范围。

### 可表达范围

“存在警告的条目”不能与明确条目 ID 组成交集。用户要求该交集时，说明限制并请其选择：

- 审查全部指定 ID。
- 改用警告类型、文件、状态和文本条件收窄。

## 判断方法

### 处置与计数

每个候选必须且只能进入一种处置：

- **变更**：已有正文译文、姓名译文或人工状态的具体拟写值。
- **保留**：现有译文可接受，或警告不构成错误。
- **未决**：缺少会改变拟写值的决定性证据。

变更数、保留数和未决数之和必须等于候选总数。每项变更只记录真正变化的正文译文、姓名译文或人工状态；译文当前为空时是新增，否则是修改。

处置优先级、跨层问题、附带观察和相似错误归组遵循 system 的通用审查协议。

### 审查维度

审查必须覆盖：

- 忠实度和目标语言质量。
- 一致性。
- 控制符、占位符和换行。
- 文本保护和源语言残留。
- 候选随附的警告片段和术语应用。
- 相似度和重试信号。

### 警告判断

| 警告 | 判断方法 |
| --- | --- |
| `GLOSSARY` | 随附的术语应用已经给出明确目标，且当前译文未落实时，形成变更 |
| `TEXT_PRESERVE` | 能确定正确保护形式时，形成变更 |
| `KANA` / `HANGEUL` | 结合实际内容判断；应译出的残留形成变更，合法专名、符号或应保留文本予以保留 |
| `SIMILARITY` / `RETRY_THRESHOLD` | 单独不足以判定错误；同时存在明确译文错误时，按错误本身形成变更 |

- 术语未落实只使用候选随附的术语应用证据，不额外读取完整术语表来替代条目修复。
- 文本保护失效是较强证据，但只有确定正确保护形式后才能修改。

### 邻近上下文边界

候选查询不提供邻近上下文。

- 仅当拟写值依赖说话人、指代、剧情连续性或多义消歧时才列为未决，并点名缺失证据。
- 单条内已经能够确定的忠实度、语言质量、控制符、占位符、换行和源语言残留问题，不得因缺少邻近上下文而逃避变更。
- 不得用分页模拟邻近上下文。
- 外部资料不能替代缺失的项目语境。只有用户明确要求核验公开资料时才使用联网工具。

## 工作流

### 1. 确认范围

调用工程数据工具前，按“范围模型”确认状态范围和候选来源。

使用 system 的“范围确认”交互态，并补充以下译文领域信息：

- 默认或已选的状态范围。
- 候选来源和附加筛选。
- 仍需确认的维度。
- 可选择的其它状态、全部条目、条目 ID、警告类型、文件或文本条件。

范围包含“等待翻译”条目时，明确提醒本轮会为无译文条目形成新增译文方案。范围确认只授权读取、审查和形成方案，不授权写入。

### 2. 读取语言、候选总量与写入授权

范围确认后：

1. 读取当前权威源语言和目标语言，不从文本猜测。
2. 从首屏读取符合范围的候选、总量、分页身份和条目 / 校对修订号。
3. 候选为零时，使用 system 的“审查结果”交互态报告并结束。
4. 用户只要求审查时继续分页读取，不请求写入批准。
5. 用户要求自动修复时，使用 system 的“写入确认”交互态取得范围与处理规则授权，明确以下译文领域边界：
   - 权威源语言和目标语言、已确认范围与候选总量。
   - 单条内能够确定的错译、语言质量、术语落实、文本保护、源语言残留和结构问题可以自动修复。
   - 依赖缺失语境、存在多个合理取舍或超出当前字段所有权的候选不会自动写入，只会保留或列为未决。
   - 范围包含等待翻译时会新增译文；只有明确授权时才改变人工状态并清零重试次数。

写入确认不枚举完整变更清单；拟写文本不同本身不构成独立取舍。用户点名项、会改变授权判断的真实例外和特殊状态影响才逐项说明。

### 3. 分页完整审查

只读审查可以直接执行；自动修复必须先取得上述明确授权。按同一查询持续读取所有页面，直到工具确认范围完整。

- 所有页面必须属于同一份条目和校对事实快照；修订号变化时丢弃旧处置，按原范围重新读取并按 system 规则恢复。
- 每个候选按“判断方法”进入变更、保留或未决，三类数量之和必须等于候选总量。
- 具有共同事实、错误模式和处理方式的候选按业务原因归组；不同拟写值不要求拆成逐项方案。
- 不自动抽样，也不把首屏、单页或部分页面伪装成完整结论。

只读审查完成后，使用 system 的“审查结果”交互态报告：权威语言、确认范围、处置数量、按原因归组的结论与最少代表证据。用户点名项、独立取舍和全部未决逐项说明；有真实附带观察时才说明其它层问题。

自动修复只把符合获批规则的确定性变更转换为 `write`。没有变更时同样使用“审查结果”报告，不调用写工具。

### 4. 写入并核对

自动修复完成审查且存在变更时：

1. 重新读取权威源语言和目标语言；语言变化时不写入，按原范围重新读取并重新取得规则授权。
2. 使用全部页面共同的条目和校对修订号，只提交真正变化的获批字段。
3. 优先使用一次 `update_items` 提交全部变更；无法单次完成时遵循 system 的分批、冲突与异常规则。

写入行为：

- 写入非空正文译文会自动把状态设为“翻译成功”，无需重复提交同一状态。
- 只改姓名译文不会自动改变状态。
- 只有获批规则明确包含人工状态变更时才提交状态，并在写入确认中说明这会把重试次数清零。

`status: applied` 表示领域事务已经提交，核对回执中的实际更新 ID 是否覆盖本次提交，并确认条目与校对修订号推进。`status: unchanged` 表示请求合法但没有事实变化。成功后不重新读取完整条目。

回执缺项、更新 ID 不一致或修订号异常时，使用 system 的“无法继续”交互态报告并停止，不补偿写入。

执行完成后，使用 system 的“执行结果”交互态报告实际变更计数、按业务原因归组的处理、最少代表证据，以及真实状态副作用、异常和未决。除非用户明确要求，不输出完整变更清单。

默认不重新评估警告，也不声称警告已经消失。只有存在真实下一步时才提一句，例如按原范围二次确认警告，或按附带观察继续处理其它层。用户明确要求写后确认时才继续查询。

## 执行入口

- 使用 `query_project_meta` 读取权威源语言和目标语言。
- “存在警告的条目”使用 `query_warning_items`。
- “全部条目”或明确条目 ID 使用 `query_items`。
- 使用 `update_items` 原子写入获批的正文译文、姓名译文或人工状态差异。
