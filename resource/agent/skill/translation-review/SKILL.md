# 译文审查

在当前工程内完成“确认范围—读取候选—根因判断—完整审查—方案确认—原子写入—结果核对”闭环。

警告是候选与证据，不直接代表错误。用户明确选择尚无译文的条目时，本技能也可以形成新增译文方案。

## 工具映射

- 使用 `query_project_meta` 读取权威源语言和目标语言。
- “存在警告的条目”使用 `query_warning_items`。
- “全部条目”或明确条目 ID 使用 `query_items`。
- 使用 `update_items` 原子写入获批的正文译文、姓名译文或人工状态差异。
- 警告查询不能与明确条目 ID 组成交集。用户要求该交集时，说明限制并请其选择全部指定 ID，或改用警告类型、文件、状态和文本条件收窄。
- 需要用户选择可表达范围时，使用 system 的“范围确认”模板。
- 工具参数始终以当前 Schema 为准。
- 本技能中的业务名称不代表额外字段。

## 1. 显式确认范围

调用工程数据工具前，必须确认两个维度：

1. **状态范围**：默认“翻译成功（PROCESSED）”。
2. **候选来源**：默认“存在警告的条目”，也可选择全部条目或明确条目 ID。

用户还可以指定警告类型、文件或文本条件。

- 两项都未明确时，一次询问两项。
- 只明确一项时，只询问缺失项。
- 两项均明确时，不重复询问。
- “默认即可”确认默认范围。

使用 system 的“范围确认”模板，并包含：

- 默认或已选的状态范围。
- 候选来源和附加筛选。
- 仍需用户确认的维度。
- 可选择的其它状态、全部条目、条目 ID、警告类型、文件或文本条件。

范围包含“等待翻译”条目时，明确提醒本轮会为无译文条目形成新增译文方案。范围确认只授权读取、审查和形成方案，不授权写入。

## 2. 读取语言与完整候选

范围确认后：

1. 读取当前权威源语言和目标语言，不从文本猜测。
2. 从首屏读取最多 100 个符合范围的候选。
3. 候选为零时使用 system 的“审查结果”模板报告并结束。
4. 候选不超过 100 时完整审查；具有共同事实、根因和处理方式的候选可以归组。
5. 候选超过 100 时使用“范围确认”模板，请用户收窄后重新读取。

范围收窄时包含当前范围、候选总数、可用筛选方式和尚未形成审查结论的说明。

本流程要求一次完整持有选定范围，不沿分页审查，不自动抽样，也不把首屏伪装成完整结论。

单轮候选上限为 100 条。超过上限时必须收窄范围，不自动分批。

## 3. 根因判断与完整审查

每个候选必须且只能进入一种处置：

- **变更**：现有事实足以确定正文译文、姓名译文或人工状态的具体差异。
- **保留**：警告合法，或现有译文可接受。
- **转交**：问题属于术语、文本保护或其它共享规则，不应通过 item 变更掩盖根因。
- **未决**：缺少上下文、说话人、剧情关系或其它必要证据，无法安全处理。

必须满足：变更数、保留数、转交数和未决数之和等于候选总数。每项变更只记录真正变化的 `dst`、`name_dst` 或 `status`；译文当前为空时是新增，否则是修改。

先判断问题拥有者，避免逐条修补共享根因：

- 单条译文本身错误：形成该条目的新增或修改方案。
- 多条候选由同一错误术语导致：归为转交，汇总证据并建议使用术语审校流程。
- 文本保护或其它共享规则导致：归为转交，报告规则层根因，不用 item 修改掩盖。
- 证据不足或警告合法：分别归为未决或保留。

审查必须覆盖忠实度、目标语言质量、一致性、控制符、占位符、换行、文本保护、源语言残留、随候选返回的警告片段、术语应用、相似度和重试信号：

- 假名残留和谚文残留可能是合法专名、符号或应保留文本，必须结合实际内容判断。
- 文本保护失效证据较强，但只有确定正确保护形式后才能修改。
- 相似度过高只表示风险，不证明错误。
- 术语未落实只使用候选随附的术语应用证据。
- 发现共享术语根因时转交术语审校，不额外读取完整术语表。
- 重试次数达到阈值只表示过程异常，单独出现时不能证明译文错误。

候选查询不提供邻近上下文。

指代、说话人、语气、剧情连续性或多义词无法由单条判断时列为未决。不得用分页模拟邻近上下文。

外部资料不能替代缺失的项目语境。只有用户明确要求核验公开资料时才使用联网工具。

## 4. 形成写入方案

使用 system 的“写入确认”模板，并包含：

- 权威源语言和目标语言。
- 已确认的状态、候选来源、附加筛选和范围完整性。
- 候选总数，以及变更、保留、转交和未决数量。
- 按共同原因归组的变更；相同处理可以归组，每组说明共同变更、数量和最少代表条目。
- 拟写值不同、独立取舍或用户点名的条目逐项列出条目 ID、文件、行号、原文、目标字段、拟写值及警告或语义依据。
- 普通保留项的分组、数量和最少代表证据，以及全部未决项的决定性证据缺口。
- 转交术语或其它共享规则处理的根因、数量和最少代表证据。

只有选定范围已完整审查时才能形成写入方案，并明确写成“选定范围已完整审查”，不得写成“全项目已审查”。范围不完整时使用 system 的“范围确认”模板请求收窄。

没有变更时使用 system 的“审查结果”模板，不请求写入批准。

审查结果包含权威语言、确认范围、处置数量、主要结论、共享根因、代表证据和全部未决项。

## 5. 写入与核对

收到明确批准后：

1. 重新读取权威源语言和目标语言。
2. 语言变化时不写入，按原范围重新读取候选、审查并确认方案。
3. 语言未变时只提交获批差异，并携带候选快照对应的条目和校对修订号。
4. 每项只提交真正变化的正文译文、姓名译文或人工状态，不重写未变字段。

完整获批集合必须一次提交，不拆分为多次写入。

写入语义：

- 写入非空正文译文会自动把状态设为“翻译成功”，无需重复提交同一状态。
- 只改姓名译文不会自动改变状态。
- 只有获批方案明确包含人工状态变更时才提交状态，并在方案中说明这会把重试次数清零。

写入后核对所有获批条目是否返回、实际字段和显式状态是否等于获批值，以及修订号是否推进。

缺项或不一致时使用 system 的“无法继续”模板，不补偿写入。

使用 system 的“执行结果”模板报告实际变更、字段核对、状态副作用、异常和未决。

默认不重新评估警告，也不声称警告已消失。在“可选后续”中说明可以按原范围二次确认警告。

用户已明确要求写后确认时才继续查询。
