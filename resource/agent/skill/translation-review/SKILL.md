# 译文审查

在当前工程内完成条目译文审查与修复：确认范围 → 读取候选 → 本层审查 → 方案确认 → 原子写入 → 结果核对。

## 目标与边界

- 本技能只写条目的正文译文（`dst`）、姓名译文（`name_dst`）或人工状态（`status`）。
- 警告是候选入口，不自动等于错误，也不自动等于可忽略。
- 用户明确选择尚无译文的条目时，可以形成新增译文方案。
- 每个候选必须得到且只能得到一项处置，选定范围完整审查后才能形成写入方案。

## 范围模型

审查范围由两个维度共同决定：

1. **状态范围**：默认“翻译成功（PROCESSED）”。
2. **候选来源**：默认“存在警告的条目”，也可选择全部条目或明确条目 ID。

用户还可以指定警告类型、文件或文本条件。

确认规则：

- 两项都未明确时，一次询问两项。
- 只明确一项时，只询问缺失项。
- 两项均明确时，不重复询问。
- “默认即可”确认默认范围。

### 可表达范围

“存在警告的条目”不能与明确条目 ID 组成交集。用户要求该交集时，说明限制并请其选择：

- 审查全部指定 ID。
- 改用警告类型、文件、状态和文本条件收窄。

## 判断方法

### 处置与计数

每个候选必须且只能进入一种处置：

- **变更**：已有正文译文、姓名译文或人工状态的具体拟写值。
- **保留**：现有译文可接受，或警告不构成错误。
- **未决**：缺少会改变拟写值的决定性证据。

变更数、保留数和未决数之和必须等于候选总数。每项变更只记录真正变化的正文译文、姓名译文或人工状态；译文当前为空时是新增，否则是修改。

处置优先级、跨层问题、附带观察和相似错误归组遵循 system 的通用审查协议。

### 审查维度

审查必须覆盖：

- 忠实度和目标语言质量。
- 一致性。
- 控制符、占位符和换行。
- 文本保护和源语言残留。
- 候选随附的警告片段和术语应用。
- 相似度和重试信号。

### 警告判断

| 警告 | 判断方法 |
| --- | --- |
| `GLOSSARY` | 随附的术语应用已经给出明确目标，且当前译文未落实时，形成变更 |
| `TEXT_PRESERVE` | 能确定正确保护形式时，形成变更 |
| `KANA` / `HANGEUL` | 结合实际内容判断；应译出的残留形成变更，合法专名、符号或应保留文本予以保留 |
| `SIMILARITY` / `RETRY_THRESHOLD` | 单独不足以判定错误；同时存在明确译文错误时，按错误本身形成变更 |

- 术语未落实只使用候选随附的术语应用证据，不额外读取完整术语表来替代条目修复。
- 文本保护失效是较强证据，但只有确定正确保护形式后才能修改。

### 邻近上下文边界

候选查询不提供邻近上下文。

- 仅当拟写值依赖说话人、指代、剧情连续性或多义消歧时才列为未决，并点名缺失证据。
- 单条内已经能够确定的忠实度、语言质量、控制符、占位符、换行和源语言残留问题，不得因缺少邻近上下文而逃避变更。
- 不得用分页模拟邻近上下文。
- 外部资料不能替代缺失的项目语境。只有用户明确要求核验公开资料时才使用联网工具。

## 工作流

### 1. 确认范围

调用工程数据工具前，按“范围模型”确认状态范围和候选来源。

使用 system 的“范围确认”交互态，并补充以下译文领域信息：

- 默认或已选的状态范围。
- 候选来源和附加筛选。
- 仍需确认的维度。
- 可选择的其它状态、全部条目、条目 ID、警告类型、文件或文本条件。

范围包含“等待翻译”条目时，明确提醒本轮会为无译文条目形成新增译文方案。范围确认只授权读取、审查和形成方案，不授权写入。

### 2. 读取语言与完整候选

范围确认后：

1. 读取当前权威源语言和目标语言，不从文本猜测。
2. 从首屏读取最多 100 个符合范围的候选。
3. 候选为零时，使用 system 的“审查结果”交互态报告并结束。
4. 候选不超过 100 时完整审查。具有共同事实、错误模式和处理方式的候选可以归组。
5. 候选超过 100 时，使用 system 的“范围确认”交互态，请用户收窄后重新读取。

范围收窄时说明当前范围、候选总数、可用筛选方式和尚未形成审查结论。

本流程要求一次完整持有选定范围，不沿分页审查，不自动抽样，也不把首屏伪装成完整结论。单轮候选上限为 100 条；超过上限时必须收窄范围，不自动分批。

### 3. 审查并形成方案

按“判断方法”审查全部候选并形成处置。只有选定范围已经完整审查时，才能形成写入方案，并准确说明“选定范围已完整审查”，不得写成“全项目已审查”。范围不完整时，请用户收窄，不形成方案。

使用 system 的“写入确认”交互态，并补充以下译文领域信息：

- 权威源语言和目标语言。
- 已确认的状态、候选来源、附加筛选，以及范围是否完整。
- 候选总数，以及变更、保留和未决数量。
- 按共同原因归组的变更。相同处理可以归组，每组说明共同变更、数量和最少代表条目。
- 拟写值不同、独立取舍或用户点名的条目，逐项说明文件、行号、原文、目标内容、拟写值及警告或语义依据。
- 普通保留项的分组、数量和最少代表证据，以及全部未决项的决定性证据缺口。
- 有真实附带观察时，说明相关术语表或保护规则仍建议后续处理。

没有变更时，使用 system 的“审查结果”交互态，不请求写入批准。仍须交代权威语言、确认范围、处置数量、主要结论与代表证据；有未决或真实附带观察时才写。

### 4. 写入并核对

收到明确批准后：

1. 重新读取权威源语言和目标语言。
2. 语言发生变化时不写入，按原范围重新读取候选、审查并确认方案。
3. 语言未变时只提交获批差异，并使用候选方案所依据的同一份条目和校对事实快照。

完整获批集合必须一次提交，不拆分写入。

写入行为：

- 写入非空正文译文会自动把状态设为“翻译成功”，无需重复提交同一状态。
- 只改姓名译文不会自动改变状态。
- 只有获批方案明确包含人工状态变更时才提交状态，并在方案中说明这会把重试次数清零。

写入后核对所有获批条目是否返回、实际内容和显式状态是否等于获批值，以及相关修订号是否推进。

缺项或不一致时，使用 system 的“无法继续”交互态报告并停止，不补偿写入。

执行完成后，使用 system 的“执行结果”交互态报告实际变更、内容核对、状态副作用、异常和未决。

默认不重新评估警告，也不声称警告已经消失。只有存在真实下一步时才提一句，例如按原范围二次确认警告，或按附带观察继续处理其它层。用户明确要求写后确认时才继续查询。

## 执行入口

- 使用 `query_project_meta` 读取权威源语言和目标语言。
- “存在警告的条目”使用 `query_warning_items`。
- “全部条目”或明确条目 ID 使用 `query_items`。
- 使用 `update_items` 原子写入获批的正文译文、姓名译文或人工状态差异。
