# 工程文件操作

工程文件的清单和顺序在 `project_meta.json` 的 `files` 中，原稿在 `sources/<file_path>`。文件变更写入 `ws.contract.changes.files`，记录结构、命名和排序规则见其 `reference`。

识别来源只读取，不需要写入授权。

用户要求添加、导入或翻译材料时，导入的完成依据都是：来源中需要翻译的文本都有归属，即进入内置资产、`.generic` 或 `.video` 资产，或已说明不处理的原因。

## 识别来源

1. 用脚本列出来源内容，例如目录结构和按类型统计的文件数。
2. 对候选入口调用 `@lg/project` 的 `inspectSources`，返回结构见 `workspace_run` 的 `@lg/project` 声明。上传文件使用 `uploads/` 开头的工作区相对路径，本机文件和文件夹使用绝对路径。
3. 按识别能力的边界核对结果：
   - `kind` 为 `game` 的资产由引擎识别，游戏是否成立以识别结果为准。
   - `kind` 为 `file` 的资产只按扩展名对应解析器，不检查内容。抽样核对内容是否符合该格式。例如 `.json` 对象按「键为原文、字符串值为译文」解析，数组按带 `message` 字段的消息列表解析，其他用途的 JSON 会产生错误条目。
4. 识别结果未覆盖的视频或纯音频，按 `video` 切段并封装为 `.video`。其他未覆盖、或内容与对应格式不符的材料，按 `generic-data` 调查其中是否有需要翻译的文本，有则提取并封装为 `.generic`，再识别产出的包。

```js
import { inspectSources } from '@lg/project';
const result = await inspectSources(['uploads/novel.txt', 'D:/Games/Demo']);
console.log(JSON.stringify(result, null, 2));
```

按结果处理：

- `game` 资产，以及内容符合格式且需要翻译的 `file` 资产，可以加入工程。
- 内容不符或不需要翻译的文件不加入工程。目录中混有这类文件时，逐个新增需要的文件，不整目录新增。
- `failures` 不为空：按 `message` 向用户说明实际原因。识别失败不等于格式不受支持。含失败项的来源不能提交，先解决失败原因，或改选不含失败项的来源。

## 组织材料

材料如何组成工程资产，由 Agent 结合用户目标判断。常见组织方式：

|情况|常见组织方式|
|---|---|
|目录是一个完整游戏|游戏根目录作为一条新增|
|目录是多个独立文件|每个需要的文件或子目录各自新增|
|游戏附带内置能力不处理的数据|游戏一条，增补数据封装为 `.generic` 另一条|
|材料只供参考|不加入工程，按参考资料使用|

- 游戏成员需要增补处理时，封装为 `.generic`，不把游戏成员作为普通资产单独新增。游戏资产已经拥有其成员和译文输出目录，单独新增会让同一内容被处理两次。
- 增补数据在游戏资产提交后，基于准备后的游戏目录调查。游戏准备可能改写目录，例如展开 ASAR、去除媒体加密，译文覆盖的是准备后的目录。

结束导入或交付前，按完成依据核对，说明哪些材料已处理、哪些有意未处理及原因、哪些尚未处理。按类型和原因归组说明，例如「已检查的图片：无待译文字，未处理」。

导入后仍有尚未处理的材料时，说明缺口后用 `ask_user` 询问，第一项为继续补齐，第二项为先处理已导入的部分。用户决定前不开始术语、翻译等后续阶段。

## 提交前确认

- `files` 中有 `kind` 为 `game` 的资产时，提交后应用会准备游戏目录，可能改写其中的文件。提交前用 `ask_user` 确认用户已经备份游戏目录，未确认时不提交。
- Godot 游戏的 `external_pcks` 至少有两个时，列出包名和当前顺序，说明后面的包会覆盖前面包中的同名资源，请用户确认顺序。确认后把完整顺序写入该来源的 `godot_pack_orders`。

自动审批不代表用户已经确认这两项。

## 准备与提交

1. 读取 `project_meta.json`，确认目标资产的 `file_path`。
2. 写入 `creates`、`updates` 或 `deletes`。
3. 按系统指令输出提交简报。删除时逐项列出目标，以及其中已翻译的条目数和页数。
4. 调用 `workspace_apply`。

- 交换两个名称时，借助一个空闲的临时名称，分三个批次依次改名。
- 需要调整新资产的位置时，在后续批次中用更新记录设置 `sort`。

删除简报的统计来自当前快照。已翻译条目指 `status` 为 `PROCESSED` 的条目，已翻译页指 `translation.kind` 为 `translate` 的页面，保留页和省略页不计入。

## 回执与恢复

- `inspectSources` 只识别来源，不能证明内容解析成功。新增回执 `parse_failed` 中的资产已经加入工程。告诉用户哪些文件解析失败，不说成新增失败。PDF 可能没有条目，但有页面。`.video` 在识别前没有条目。
- `invalid_change` 提示 Godot 包集合已变化时，重新识别来源，与用户确认新的完整顺序。
- 错误 `data.committed_sync_failed` 时，先重读工程确认已生效的文件变更，避免重复提交。

## 更新文件

用新版本来源更新工程中已有的资产时，先新增新版并继承译文。旧资产留作对照，确认结果后再删除。

1. 按名称、格式和内容判断每个新来源对应的旧资产。无法判断时用 `ask_user` 询问。没有对应旧资产的来源按普通新增处理，没有对应新来源的旧资产保持不变。
2. 新增记录写入 `inheritance_mode: "inherit"`，按「准备与提交」提交。页面译文不继承。
3. 用脚本按 `row_number` 对齐新旧资产的 `src` 序列，把新资产中仍未完成的条目和回执 `contested` 中的条目分类：

|类别|判断依据|处理|
|---|---|---|
|差异项|能对应到旧条目，或属于 `contested`|参考旧译文，按 `translation` 的条目修正资源改写并提交。这一步属于更新流程，不再询问翻译流程|
|新增内容|没有对应的旧条目|不翻译，只统计条数|
|异常|大部分旧译文找不到对应，或大段连续对不上|不修复。说明实际数量和抽样，指出可能原因，例如来源或版本不对、语言不同、格式或提取方式变化，新旧资产都保留|

4. 没有异常时，修复差异项后用一次 `ask_user` 询问后续，选项为删除旧资产并翻译新增内容、仅删除旧资产、保留旧资产。没有新增内容时去掉翻译选项。旧资产没有已翻译条目和页面时不询问，直接删除。
5. 删除旧资产时在同一批次中：
   - 新资产取旧资产的 `sort`。
   - 回执 `renamed` 显示新资产因与旧资产同名而改名时，改回旧名。
6. 用户决定旧资产去留前不生成译文。用户选择保留时，新旧资产都不改动。

## 生成与交付

先核对 `project_meta.json` 的 `files`。没有工程文件时，向用户说明当前没有可生成译文的材料，并引导添加文件。用户已提供材料且已授权导入时，继续完成导入后再生成。

生成前结合内容、结构和用途，判断工程中是否真正包含电子书或字幕。检查通用包内部材料。资产类型与扩展名只作为线索。README、安装说明等附带文本不触发双语输出。无法确定时，说明疑点并用 `ask_user` 询问。用户回答后再生成。

全部资产生成单语成果。仅为确认属于电子书或字幕的内容生成双语成果。将包含这些内容的资产的 `file_path` 组成 `bilingual_files`。没有则使用空数组。

1. 按 `project_meta.json` 的 `files` 中的 `file_type` 加载对应的格式技能。有 `GENERIC` 时加载 `generic-data`，有 `VIDEO` 时加载 `video`。
2. `counts.items_with_warnings` 大于零，且用户本次尚未决定是否审校、本对话也未完成审校时，用 `ask_user` 询问。第一项为直接生成，第二项为先审校再生成。选择审校时加载 `translation`。完成审校后继续。
3. 提交本次交付所需的工程变更。再调用 `@lg/project` 的 `generateFiles(bilingual_files)`。
4. 有 `GENERIC` 时，按 `generic-data` 用 `generic_input_path` 中的写回输入还原目标格式。有 `VIDEO` 时，按 `video` 渲染字幕。宿主未生成的双语成果按对应格式制作并验证。写回输入属于工作材料，不放入成果。
5. 对照 `files` 核对原生产物与通用写回成果的完整集合。路径重叠时结合真实加载方式安排合并。带 `.reference` 标记的文件须结合资产来源和格式技能判断，不能只凭名称作为可安装文件交付。用户要求打包时，打包核对后的成果。
6. 确定交付目录：
   - 用户指定了位置时，调用 `getOutputPaths(该目录)`。
   - 否则调用 `getOutputPaths()`。`manual` 为 `true` 时用 `ask_user` 询问。第一项为留在工作区，第二项为写入返回的 `translated_path`。用户输入的自定义内容作为父目录。再调用 `getOutputPaths(该目录)`。
   - 选择留在工作区或取消时，在工作区交付。
7. 需要写入工作区外时，把单语成果写入 `translated_path`。实际生成的双语成果写入 `bilingual_path`。没有双语成果时不创建或复制双语目录。目标已存在时，沿用已选父目录重新调用 `getOutputPaths` 取得新路径。只写入已核对的成果。说明双语覆盖范围。
8. 说明交付位置、格式技能要求的交付说明、验证结果和未完成范围。生成或写入失败时，检查已完成的文件再补齐缺口。把失败残留和写回输入标为工作材料。
