# 通用数据处理

后端保存底稿与确定的解析结果。格式调查、语义判断、定位解释和写回由你完成。容器入口和记录结构见 `workspace_run` 的 `@lg/project` 生成接口说明，以该机器契约为准。

## 调查与分组

先读取相关工程知识，确认用户目标和材料来源。历史来源路径只提供线索，实际使用前检查可用性。游戏文件清单和引擎技能可帮助找出未处理的数据，按当前目标调查，无需先完成全盘调查。

- 结合消费代码、编码、结构和上下文区分显示文本、资源路径、程序标识和控制片段。无法判断的内容记录依据与缺口。
- 独立文件分别成包，便于单独替换。索引与数据体、共用字符串表或跨文件偏移需要共同写回时放在同一包。
- 冻结选定的底稿字节后再提取，解析结果必须对应包内同一份底稿。源文件若占用固定入口名，放入子目录。
- 使用 Node、`@lg/python`、`@lg/npm` 和第三方库按需处理。脚本、说明和其他资源可随包保存，存在脚本不代表未来可以未经检查直接执行。

## 提取与入库

1. 确认可翻译字段，保持每条记录的定位与数组顺序。私有定位可表达记录索引、字段、偏移或其他实际坐标，由你解释。
2. 把底稿与解析结果封装成 `.generic` ZIP，建议使用 `STORE`。包内不保存工程当前译文或翻译状态。
3. 提交前校验固定结构、定位对应关系和提取语义。空数组只表示本次没有记录，不能作为调查完成或无需翻译的证据。
4. 按 `project-operation` 识别、提交并核对回执。
5. 文件变更成功后，在后续批次按真实资产路径保存必要知识：材料关系、定位含义、提取方法、依赖与版本限制、语义判断、验证结论和未决事项。

发现遗漏、误提取或定位变化时，重新生成完整包，通过 `updates.source_path` 整包替换。宿主重建条目并继承译文。不能把数据库 `item_id` 当作原文件坐标，也不能直接按旧行号搬译文。

## 写回与交付

生成与最终交付按 `project-operation` 的「生成与交付」执行。使用本次 `generateFiles()` 返回的 `generic_input_path` 完成以下处理：

1. 读取目标资产的写回输入。它与源解析结果按数组下标对应，正文与姓名已确定。脚本只按私有定位写回底稿。
2. 在 `work/` 中完成写回。按实际格式处理长度、偏移、索引、编码、转义、校验和及字段间依赖。
3. 按下文验证写回成果。写回输入和未还原的底稿属于工作材料。

## 验证

- 用真实变化的译文做写回样例，再重新读取。原文不变的往返不能证明写回有效。
- 文本样例检查编码、语法、引用、控制标记和未修改字段。二进制样例至少检查本次触及的长度或索引约束。
- 抽样检查可能漏提取或误识别的字段，结合消费代码或领域证据确认。需要运行验证时执行有界验证，记录尚未覆盖的路径。
- 依赖缺失、解析失败或生成失败时检查实际产物，修复后从可靠材料继续。将验证结果和继续条件写入相关工程知识。
