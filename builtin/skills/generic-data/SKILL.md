# 通用数据处理

后端保存底稿与确定的解析结果。格式调查、语义判断、定位解释和写回由 Agent 完成。容器入口和记录结构见 `workspace_run` 的 `@lg/project` 接口说明，以该机器契约为准。

本技能提供通用包的流程，具体格式的方法由对应的引擎技能提供，两者一起加载。

## 来源调查

导入时按 `project-operation` 的完成依据调查来源。补漏或修订已有包时，只调查受影响的材料。

- 结合引擎技能、游戏文件清单和消费代码定位文本所在的文件与对象类型。
- 未命中的文件或对象类型按类型给出抽样依据，说明为何没有待译文本。
- 结合消费代码、编码、结构和上下文区分显示文本、资源路径、程序标识和控制片段。无法判断的内容记录依据与缺口。
- 同一个值既用于查找又用于显示时，保留原值，在最终显示处映射译文。

## 导入准备

- 独立文件分别成包，便于单独替换。索引与数据体、共用字符串表或跨文件偏移需要共同写回时放在同一包。
- 冻结选定的底稿字节后再提取，解析结果必须对应包内同一份底稿。源文件若占用固定入口名，放入子目录。
- 使用 Node、`@lg/uv`、`@lg/npm` 和第三方库按需处理。
- 包内必须包含再次写回所需的写回程序、依赖声明和定位说明。依赖声明记录 npm 与 Python 包的名称和版本。定位说明写明适用的引擎技能。`work/` 会随对话重置或工作区回收消失。包内程序仍须读取、检查后再执行。

1. 按「写回与验证」的代表样本确认解析和写回方法。
2. 确认可翻译字段，保持每条记录的定位与数组顺序。私有定位可表达记录索引、字段、偏移或其他实际坐标，由 Agent 解释。
3. 把底稿与解析结果封装成 `.generic` ZIP。使用 `STORE`，避免与入库压缩重复。包内不保存工程当前译文或翻译状态。
4. 提交前校验固定结构、定位对应关系和提取语义，按「写回与验证」的全量清单核对覆盖。空数组只表示本次没有记录，不能作为调查完成或无需翻译的证据。

产出的包交回 `project-operation` 识别、提交并完成导入收尾。

发现遗漏、误提取、定位变化或包内缺少写回材料时，重新生成完整包，按 `project-operation` 的「更新文件」提交。不能把数据库 `item_id` 当作原文件坐标，也不能直接按旧行号搬译文。

## 写回与验证

在 `project-operation` 的「导出与交付」中，使用本次 `generateFiles(bilingual_files)` 返回的 `writeback.input_path` 完成以下处理：

1. 读取目标资产的写回输入。它与源解析结果按数组下标对应，正文与姓名已确定。脚本只按私有定位写回底稿。
2. 在 `work/` 中完成写回。按实际格式处理长度、偏移、索引、编码、转义、校验和及字段间依赖。
3. 按下文验证写回成果。写回输入和未还原的底稿属于工作材料。

以下三类依据各自证明一件事，不能互相替代。

### 代表样本确认方法

每种格式或对象类型先用代表样本确认解析、语义判断和写回方法。样本覆盖可变长度、列表、可选字段等影响布局的情况。

- 未改动时先验证往返。要求无损保留的区域逐字节一致，重新序列化的区域核对结构与字段值。
- 用真实变化的译文做写回样例，再重新读取。原文不变的往返不能证明写回有效。
- 文本样例检查编码、语法、引用和控制标记。二进制样例至少检查本次触及的长度或索引约束。
- 结合消费代码或领域证据抽查可能漏提取或误识别的字段。抽查结论用于确认判断方法，不替代全量清单。

### 全量清单确认覆盖

列出全部候选文件或对象，每项最终归入以下一类，记录定位与依据：

- 已提取：记录进入的包与私有定位。
- 有依据地排除：说明无待译文本或不处理的原因。
- 解析失败：记录失败原因，转入单独调查。

仍有解析失败或未归类的候选时，不能报告来源已全部处理，按 `project-operation` 的完成依据说明剩余范围。已提取部分全部写回成功，不代表来源中的文本全部处理完成。

### 全量机械比较确认写回

- 每次写回后重新读取全部记录，逐条核对定位、目标字段和写入值。
- 写回范围外的对象、区域和文件逐一比较字节或哈希，确认保持不变。
- 至少一次只使用工程中的包内材料，在没有既有 `work/` 产物的条件下完成真实译文写回，证明清理工作区或换机后仍可恢复。

需要运行验证时执行有界验证，记录尚未覆盖的路径。依赖缺失、解析失败或生成失败时检查实际产物，修复后从可靠材料继续。
