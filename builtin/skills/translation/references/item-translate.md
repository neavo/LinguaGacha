# 条目翻译

本流程为条目形成完整译文，适用于翻译、补译、续做和重译。

- 术语见 `SKILL.md`。
- 译文质量按 `writing-guide` 的 `references/translation-guide.md` 判断。
- 格式专属要求按已加载的格式技能执行。

## 1. 确定目标

通过 `ws.contract` 读取 `project_meta`、`items` 和关联的 `warnings`，再按用户请求确定目标：

|请求|目标|
|---|---|
|翻译，未限定范围|状态为 `NONE` 的条目|
|补译|用户指出的遗漏|
|重译|用户指定的条目，只替换用户允许替换的内容|
|续做|对照最新快照和业务工作材料，找出剩余目标和未决目标|

续做时，未提交的变更清单和已写入的工程数据分开判断。

用户指定以下条件时，将条件解析为具体目标，再按 `item_id` 去重：

- 文件
- 条目
- 状态
- 文本条件
- 排除项

按条目状态决定是否纳入目标：

|状态|纳入条件|
|---|---|
|`ERROR`|沿用用户已明确的重试决定。没有决定时，说明数量，并用 `ask_user` 提供重试或跳过选项|
|`PROCESSED`|只在补译或重译时纳入|
|`EXCLUDED`、`RULE_SKIPPED`、`LANGUAGE_SKIPPED`、`DUPLICATED`|只在用户明确指定时纳入|

按以下规则将目标分成业务单元：

- 单元规模按 `分组与提交` 执行，按需要分别判断的条目计数。
- 按文件和来源顺序组织目标。
- 共享语境、跨条目表达或指代关系紧密的目标放在同一单元。
- 将正文、姓名、警告和命中片段关联到所属条目。

## 2. 选择执行者

`batch_item_translation` 只按 `item_ids` 和 `item_statuses` 筛选条目。它使用工程提示词翻译，并直接写入工程。

从上到下选择第一条符合的条件：

|条件|执行者|
|---|---|
|`report` 任务，或用户要求统一提交、写入前先审阅|Agent|
|用户对译文提出了工程提示词之外的要求|Agent|
|目标不超过一个业务单元|Agent|
|其余情况|`batch_item_translation`|

目标分属不同执行者时，分别安排。在业务工作材料中记录每个目标的执行者。

## 3. 形成译文

Agent 逐个业务单元执行以下步骤：

1. 读取原文、现有译文、姓名和必要语境。
2. 缺少参与者、指代或剧情事实时，用 `@lg/workspace/item-contexts` 的 `queryItemContexts` 查询邻近语境，再围绕具体缺口取证。
3. 按 `translation-guide` 形成译文。补查后仍缺少决定性事实时，将条目记为未决。
4. 按「条目约束」检查译文的结构。
5. 按 `translation-guide` 的「检查质量」逐项检查本单元。
6. 检查通过后，按 `分组与提交` 提交。

统一提交或 `report` 任务时，将本单元检查通过的变更清单保存到业务工作材料。保存后再处理下一单元。

### 条目约束

|约束|要求|
|---|---|
|边界|每条原文对应本条的完整译文。保留条目的边界、顺序、行数和换行|
|跨条目语境|可以结合跨条目语境理解内容。只按用户的明确要求改变结构|
|保护结构|控制符、占位符、标签、转义和其他保护结构保持位置与边界|
|标点|引号、括号可以转换为目标语言的同类形式。原文的半边结构和跨条目延续的结构保持原样|
|姓名|`name_dst` 只写姓名译文。称谓、头衔、敬称和解释留在正文的对应位置|
|提交字段|按 `ws.contract.changes.items.updates.reference` 提交字段修改或显式状态意图|

## 4. 批量执行后

`batch_item_translation` 结束后，执行以下步骤：

1. 读取最新快照。
2. 对照工具结果，核对成功、失败、排除和剩余目标。
3. 在业务工作材料中记录实际读取和做过语义判断的范围。
4. 将已读译文和关联 `warnings` 中的具体线索交给「6. 关联检查」。
5. 出现新的失败目标时，按「1. 确定目标」中的重试决定处理。

## 5. 记录

业务工作材料按 `item_id` 保存以下内容：

- 未提交的变更清单
- 每个目标的当前结论
- 未决目标的缺失事实、已查材料、已尝试的译法和继续条件
- 待处理的关联问题，包括发现依据、影响范围、检查方法和当前状态

按任务规模组织业务工作材料。上下文重置后，这些记录要足以恢复剩余目标和每个目标的执行者。

## 6. 关联检查

翻译、读取语境和核对结果时发现以下线索，需要检查其他目标：

|线索|检查对象|
|---|---|
|后文确认了姓名、身份或关系|已经使用相关译名或指代的目标|
|结构损坏或命题错配|相同条件下的同类表达|
|可靠的译法|同系列表达和人物声音是否一致，并结合语境和剧情阶段确认适用|

新证据改变身份、译法、结构、变更清单或未决结论时，检查本次范围内受影响的目标。

关联检查遵守以下规则：

- 检查发现新问题时，继续处理。
- 原问题修正后，仍要完成已经产生的后续检查。
- 所有相关影响都有结论后，才结束关联检查。
- 合并等价问题，复用有效证据。
- 只重查变化影响的部分。

每次写入并读取回执后，执行以下步骤：

1. 读取最新快照。
2. 核对成功的目标、译文、关联 `warnings` 和状态等字段的变化。
3. 写入后发现的问题同样按本节处理。

修改已写入的条目时，使用最新快照中的数据和 `fp`。

## 7. 结束与交付

结束前对照全部目标和问题记录，逐项确认：

- 每个目标都已写入、保存在变更清单中，或记为未决。
- 变更清单完整并通过检查。
- 批量结果已核对。
- 已发现的关联影响都有检查结论。

还有可以执行的剩余工作时，继续处理。

交付时说明以下内容：

- 覆盖的目标和实际做过语义判断的范围
- 每部分的执行者和完成结果
- 按 `item_id` 去重后，已完成、已排除和剩余目标的合计是否覆盖用户要求的范围
- 正文修改数、姓名修改数和警告数各自的统计方法
- 引用的数字来自变更清单、本轮批量统计还是工程累计进度
- 未决目标的缺失事实、已查材料和继续条件
- 格式技能要求的其他交付内容

同一条目的多个问题合并展示。
