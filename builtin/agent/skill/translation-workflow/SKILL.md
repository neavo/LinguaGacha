# 翻译工作流

先确定任务目标、处理范围和执行方式，由 Agent 判断文本时，加载 `self-inspiring` 和 `translation-rules`，按前者组织后续调查，按后者检查译文。

## 1. 确定任务目标

任务类型和是否实际写入遵循 System Prompt，本技能补充以下默认行为：

|用户要求|默认动作|任务类型|
|---|---|---|
|翻译、补译、修正、重译或落实审查建议|形成译文、检查并写入工程|`apply`|
|审查译文|检查现有译文，报告问题和建议|`report`|
|审校译文|检查现有译文，发现问题并写入修正结果|`apply`|

## 2. 确定条目范围

全量翻译和按文件、章节、item 或文本条件补译使用同一流程。工程外文本在已授权导入后，读取当前工程事实确定范围。

对于翻译执行任务，范围内存在失败条目且用户尚未决定是否处理时，调用 `ask_user` 说明数量，依次提供「处理失败条目」「跳过失败条目」，根据工具返回的决定确定目标，已有明确决定直接沿用，等待、到期和取消按工具说明执行。

普通待译条目和用户决定重试的失败条目构成翻译目标，按 item 身份去重，正文与姓名字段一起处理，其它状态、排除项、跳过项和重复项按用户范围与工程契约确定。

分别说明需要读取哪些条目，以及本次可以修改哪些条目和字段，范围外 item 只提供已授权的语境、一致性或边界证据。

补译处理全部明确的未译目标，审查与审校按以下方式确定对象：

- 用户要求逐条审查或审校时，使用 `candidate_policy: all`，范围内全部符合条件的 item 都要判断。
- 主动发现问题时，使用 `candidate_policy: discovered`，从警告、分散样本和领域检查方向发现候选。
- 用户只指定警告或某些 item 时，遵守这一范围。

## 3. 选择执行方式

先通过计数和必要抽样估算翻译规模，再按 System Prompt 的业务单元规则分组。按下表选择适合的执行方式，工具能否调用统一遵守 System Prompt 的“工程写入边界”：

|本阶段任务|执行方式|
|---|---|
|没有待处理翻译目标|说明当前状态，继续用户要求的其它阶段|
|翻译目标只有一个业务单元|Agent 在工作区形成译文并检查|
|翻译目标超过一个业务单元|调用 `run_batch_translation` 处理本阶段全部选定翻译目标|
|已有译文审查、审校、修正、明确重译或落实审查建议|Agent 在工作区逐项判断和处理|

按公共工具边界改用 Agent 分析时，继续按业务单元处理用户要求的全部范围。组合任务分别安排翻译、审查或审校阶段。Agent 自动完成分流，开始时说明范围、数量和执行方式。Agent 翻译使用当前模型，批量翻译使用保存的批量模型偏好，实际配置由宿主展示。

使用批量工具前，将范围解析为明确 item 身份，提交、结果字段、快照刷新和停止按该工具契约执行，正常结束后继续已授权阶段，工具停止后暂停依赖该运行的工作。

引擎重试结束后报告实际失败和剩余范围，本轮新产生的失败条目不自动启动新阶段，后续处理使用第 2 节的失败条目决定规则。

## 4. Agent 逐项处理和检查

`translation-rules` 提供初始检查与独立发现方向，`self-inspiring` 组织探查、判断与回流。

按 `project_meta` 的文件顺序和文件内顺序组织业务单元。每个 item 记录当前工作：待译和用户同意重试的失败条目使用 `translate`，已有译文审查或审校使用 `review`。`review` 表示判断已有译文的工作类别，审查与审校共用该值；是否写入由 `scope.result` 按 System Prompt 决定。组合任务可以包含两类对象。

每个业务单元完整处理全部 targets，按 `translation-rules` 执行：

1. 取得当前原文、正文与姓名译文、状态及相关警告；补足命题、参与者、关系和剧情阶段所需的邻近语境。
2. 形成拟写值前读取或复用适用术语证据，确认结构保护、姓名槽位与条件术语的适用边界。
3. 按原文事实和 `writing-guide` 形成或核验译文，保持含义、声音、语气、强度、有意歧义、信息时机与文本功能，并核对同类表达的一致性。
4. 对正文与姓名形成同一个 item 的 `update / keep / blocked` 结论，记录实际拟写字段；未决保留决定性缺口、已完成补证和解除方式。
5. 核对单元内每个目标均已处置，拟写值通过结构、命题、身份、术语和表达质量检查。失败项先补证或修正；新模式、关系与受影响结论进入自启发后继探查。

广泛主动审查与审校均落实结构完整性、命题关系、身份指代、译名与表达一致性四类独立方向；扫描与语义样本分别记录实际范围。定点任务遵循声明边界。单元完成后保留后继方向，继续全任务的发现和关联核验。

补译得到的译文先按形成标准核验。用户还要求后续审查或审校时，依据新译文安排该阶段，复用仍有效的证据。

## 5. 提交安排与写入后检查

默认按业务单元安排提交：每组检查通过后，按 System Prompt 的“交付或提交处理结果”处理该组结论，再继续下一组。字段及人工处置的含义按 `translation-rules` 确定。

写入后核对实际译文、warnings 和相关字段副作用，结果提示新问题时，按 `self-inspiring` 重新检查受影响对象。

## 6. 最终检查与交付

完成 `self-inspiring` 要求的调查和停止检查后，核对：

- 翻译、审查、审校和其它要求的阶段已覆盖用户范围，实际候选符合 `all / discovered` 策略。
- 适用的独立方向与后继探查均已完成，程序扫描、分页与语义样本的真实覆盖可追溯，最近整轮增量已核验并稳定。
- 每个 item 的正文和姓名只有一个当前结论，未决记录缺什么、查过什么及怎样继续。
- 方案中的字段和变更清单一致，准确表达已确认的处理结论。实际写入的回执及副作用在第 5 节核对。
- 方案中的译文、术语应用和结构已经检查。

验收失败时补证或修正受影响对象；新证据或缺口按自启发协议回流，重新稳定并验收。还有可执行工作时继续，因阻塞结束时说明未完成部分，任务完成条件遵循 System Prompt。

按 System Prompt 的范围、数量与证据要求，补充各阶段实际完成情况、候选策略，以及按 item 唯一当前结论统计的 `update / keep / blocked` 数量。问题类型可能在同一 item 上重叠，按其实际影响解释主要问题与未决。批量阶段本轮结果、工程累计进度和 Agent 处理计数分别说明。只有使用 `all` 且实际逐项检查完整时，才声称完成逐条语义审查。

## 7. 任务记录

使用 `self-inspiring` 的共同记录，并补充：

|记录|内容|
|---|---|
|`scope`|`result: report / apply`；翻译、审查、审校或组合阶段；item、状态、文件、警告或文本条件；`candidate_policy: all / discovered`；是否主动发现；可写字段、排除项和语境读取边界|
|`targets`|item 身份、当前 `translate / review` 工作、已完成阶段、正文与姓名的 `update / keep / blocked` 结论、完整待写字段和依据|

方案内容与实际工程事实分别记录，中断后依据当前事实和保留的任务记录继续未完成阶段。文件保存与恢复按 `self-inspiring` 执行。
