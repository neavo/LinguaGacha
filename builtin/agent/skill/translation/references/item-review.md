# `items` 审校

本流程用于检查、审校和修正工程中的已有或拟议译文。

## 目标与范围

用户要求审校时，按其要求确定范围，未限定时覆盖当前工程全文。用户指定问题或对象时，围绕指定目标及其必要关联开展调查。用户要求逐条审校时，对范围内每个适用条目完成所要求的判断。

从完整的 `items` 中确定范围内已有正文译文、姓名译文或拟议译文的适用条目。审校拟议方案时，按 `item` 身份关联工程并记录译文来源。

按全局 `业务单元与提交` 的默认规模分组，以需要分别判断的 `item` 计数。按文件和来源顺序组织目标，将共享语境或跨条目表达的目标放在一起判断。将正文、姓名与多个警告关联到所属条目，按 `item` 身份去重后统计覆盖范围。

## 冷启动

用户指定问题或对象时，先调查指定目标及其必要关联。审校时优先按 `item` 身份关联相关 `warnings`，读取原文、译文和必要语境。工程警告针对已写入的值，审校拟议方案时要根据拟议值重新判断。

没有相关警告时，在任务范围内按文件结构、来源顺序和内容分布合理均匀采样。实际读取至少一个完整业务单元，保留完整语境和对象关联。

按下文领域要求判断初始材料，再从成立的问题、误报、正确译法和其它结果中提炼种子。

## 种子发现思路

冷启动和后续调查都可参考以下思路寻找种子。根据任务目标和当前证据按需选择，也可沿材料揭示的其他关系展开。

- **警告线索**：从成立问题、误报及其关联关系寻找适用条件，调查同类用法。
- **信息完整**：从遗漏、增添、重复，以及数字、单位、限定条件和局部片段的对应关系寻找问题模式。
- **结构保持**：从 `item`、换行、控制符、占位符、标点及跨 `item` 延续结构寻找损坏或正确保持的规律。
- **命题关系**：从参与者、施受、归属、修饰，以及否定、数量、时间、因果和情态的作用对象寻找关联句式。
- **身份与指代**：从人物关系、剧情阶段、姓名、称谓、代词、别名和术语条件寻找身份与固定译名的适用边界。
- **表达与功能**：从自然表达、人物声音、语气、强度、文本用途、同系列译名和替代表达寻找一致性线索。正确译法、同词异义和有意保留的不规则表达都可启发调查。
- **事实与方案变化**：从新语境、关系、术语条件、覆盖缺口和提交后事实变化寻找需要重查正文与姓名的对象。

例如，发现施受关系译反后，调查相同句式。若结果显示错误与视角切换后的主语省略有关，再调查这一组合条件，并用正确译法和反例核验边界。

## 种子列表与循环执行

在本任务的 `work/` 子目录中维护一份种子列表。每个种子只记录以下两项：

|字段|含义|
|---|---|
|模式|根据实际材料或调查结果提出规律、关系或问题，写清触发证据、调查对象、适用条件和核验方法|
|是否消耗|是否已完成该模式的取证、结果处理和后续种子提炼|

将新增种子标为未消耗。冷启动完成后，至少再完成一轮调查，包括取证、结果处理和后续种子提炼。

初始结果暂时无法形成关联种子时，从尚未检查的材料中寻找线索：选择另一个能补充调查视角的业务单元，记录待查模式，再读取材料并判断。

已读完任务范围内的材料并完成所需核验时，记录完成依据。材料或工具受阻时，记录未完成的调查和继续所需的条件。

按以下步骤循环调查：

1. 选择未消耗的种子，按下文领域要求取证、判断并处理结果。相关模式可以合批调查。
2. 从错误、正确案例、反例、关系和证据缺口中提炼后续模式，与已有种子比较。合并等价模式，复用有效证据，将新模式加入列表。同类实例补充到业务工作材料中。
3. 新事实改变已有模式的适用条件或结论，需要重查时，更新该模式并标为未消耗。发现范围外的问题时，说明调查理由，交由用户决定。
4. 完成取证、结果处理和后续提炼后，将对应种子标为已消耗。根据新事实仍需补查该模式时，将它保留为未消耗。继续处理列表中未消耗的种子。

直接更新种子列表。在业务工作材料中保存证据、对象结论、完整方案、实际处理范围和具体未决事项，用文件位置和对象身份关联这些记录。

### 循环结束与任务完成

结束自启发循环前，确认以下条件均已满足：

- 已消耗列表中的全部种子。
- 已完成冷启动后的至少一轮调查，或已读完任务范围内的材料并完成所需核验。

将未完成或受阻的种子保留为未消耗。暂停调查时，说明原因和继续所需的条件。

交付前，核对用户要求的覆盖范围和领域成果。还有指定对象需要处理时，继续完成判断，并用新事实补充或更新种子。在业务工作材料中记录循环结束或受阻的依据。

## 领域判断与成果核验

冷启动和种子调查都按以下要求处理目标。

按稳定 `item` 身份保存完整发现集合、正文与姓名的当前结论、证据和待写入字段。分别记录程序扫描与实际语义阅读的范围。

### 1. 读取证据

调查条件可以用程序定位目标时，扫描声明范围内的全部数据并读完所有分页。模型根据原文和必要语境判断。

需要核对参与者、身份和上下文衔接时，先用 `@lg/workspace/item-contexts` 的 `queryItemContexts` 取得邻近语境，再补查影响判断的缺失事实。结合人物关系、语境和剧情阶段，判断已有译法是否适用。

补查后仍有歧义时，检查已有译法是否忠实保留了歧义，以及证据是否支持修正。仍无法判断时，记录缺失事实、已查语境、已尝试的解释和继续条件。继续处理可独立确定的条目。

警告线索按以下问题核验：

|警告|需要核验的问题|
|---|---|
|`SIMILARITY`|是否漏翻，原文信息与功能是否已表达|
|`FOREIGN_CHAR_RESIDUE`|是否局部漏翻，是否存在浊音、语气词残留等|
|`TEXT_PRESERVE`|是否存在无需翻译的结构文本被误翻|
|`GLOSSARY`|术语落实情况是否正确合理|
|`PUNCTUATION_MISMATCH`|标点符号的结构、位置及用法是否正确|
|`RETRY_THRESHOLD`|最终放行的译文是否正确，然后提交任意变更将次数置零|
|`LINE_COUNT_MISMATCH`|原文与译文的行数是否对齐|

### 2. 判断、修正与单元提交

按稳定 `item` 身份为正文与姓名形成一个当前结论：修正、保留或未决。保存判断依据和完整待写入字段，按以下要求修正：

- 保留 `item`、行数、换行及保护结构边界。
- 姓名槽位只保存姓名，称谓和解释在对应正文中表达。
- 按原文中的实际作用保留半边标点与跨 `item` 结构。

逐项核对当前单元中正文与姓名的结论、修正依据和完整待写入字段，通过后按全局 `业务单元与提交` 安排提交。默认提交本单元并核对结果，再进入下一单元。统一提交时，先保存方案再处理下一单元。`report` 保存检查通过的方案后，继续调查。

按 `ws.contract.changes.items.updates.reference` 所述契约处理字段、人工状态、接受译文、重试计数和同文组副作用。实际写入后核对译文、`warnings` 及相关副作用。

### 3. 核对成果

- 记录实际调查范围、证据和种子的处理结果。
- 核对用户指定目标和全部发现对象的当前结论。
- 完成当前种子涉及的对象处理。遇到阻碍时，在业务工作材料中说明原因，并将对应种子保留为未消耗。
- 核验方案变化对相关对象的影响。
- 检查最终待写入字段。

核对用户要求的逐条覆盖、当前种子的检查范围与修改影响。发现缺口时完成对应调查和判断，实际写入产生的新事实同样用于种子提炼。

## 交付

交付时提供种子列表和业务工作材料链接，并说明：

- 代表性模式，以及循环结束或受阻的依据。
- 实际调查、程序扫描和语义判断的范围。
- 代表性问题、修正与保留数量、未决事项和实际写入结果。

按 `item` 身份统计方案中的修正、保留和未决数量，每个条目只计入一类。条目仍有影响结论的未决问题时，将其计入未决，并保存已经确定的修正。

核对三类数量的合计是否与实际已判断条目数一致，并说明尚未判断的范围。问题类型和警告可以重叠，说明各自的统计方法。按回执统计实际写入数量。

记录拟议方案时注明它与工程现值的区别。没有发现问题时，说明实际检查范围与依据。完成范围内每个适用条目的判断后，才称完成全量逐条审校。
