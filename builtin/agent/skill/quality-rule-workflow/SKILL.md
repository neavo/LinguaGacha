# 质量规则工作流

## 技能加载与责任

加载并遵循 `self-inspiring` 技能；涉及 glossary 时加载 `glossary-rules`，涉及 text_preserve 时加载 `text-preserve-rules`。领域技能负责对象资格、发现依据和安全表达，自启发技能负责从这些判断持续生成后继探查、回流核验和整轮稳定判定。

本技能拥有质量规则任务范围、既有规则参与方式、领域附加记录、目标集合验收与提交安排。按“固定范围 → 建立领域前沿 → 自启发循环 → 目标集合验收 → 结果交付”推进。

## 1. 固定任务范围

调查范围决定读取哪些工程事实，调整范围决定可以形成哪些业务结果。用户的查询、审查、讨论和计划形成 `report`；明确修改目标形成 `change`。指定阶段、规则类型、对象或允许操作时按其限定执行。

仅调用本技能且未给出进一步目标时，默认对当前工程两类规则开展既有规则审校与未覆盖对象发现，形成 `report`；将该默认范围与既有规则策略 `all` 明确写入 scope。

|用户目标|领域与既有规则策略|
|---|---|
|未限定类型的质量规则任务|glossary 与 text_preserve|
|术语、名称、译名或实体|glossary|
|控制符、占位符、格式结构或文本保护|text_preserve|
|提取新规则|发现未覆盖对象，既有规则默认只作为证据|
|审校既有规则|核验范围内全部既有规则；主动提取按用户目标确定|
|维护指定规则|指定对象作为调整目标，其余规则提供覆盖、冲突和边界证据|

`scope` 记录 `result: report / change`、`kinds`、调查与调整范围、`allowed_actions`、`target_entry_ids`、`existing_entry_policy: all / listed / evidence_only`，以及是否包含发现未覆盖对象的目标。未按既有 ID 限定时 `target_entry_ids` 为 `null`。没有指定 ID 的整体维护使用 `all`，新增任务使用 `evidence_only`，定点维护使用 `listed`；用户要求优先。

质量规则的覆盖、关系与集合最小性需要共同验收。工程变更先完成全部业务单元，再将验收通过的目标集合统一准备为一个提交批次；实际结果以提交回执为准。

## 2. 建立领域发现前沿

items 是默认事实来源；缺少片段、顺序、层级或容器结构时依据 `project_meta` 定点读取 sources。

前沿包含用户指定对象、既有规则核验、领域规定的独立方向，以及符合 glossary 领域判据的 `seed: true` 条目所启发的关联方向。全部既有条目都参与其适用的覆盖、冲突和边界核验。`seed` 的当前值与证据保存在任务对象中，更新与回流按 `self-inspiring` 执行。

包含发现未覆盖对象的任务，至少完成三个具有实质不同范围或方法的独立工程方向，同时满足各领域的证据基础要求。纯既有规则审校或定点维护依据声明范围建立前沿。

同一任务包含两个领域时，术语语境中的固定标记可以启发保护调查，结构槽位中的名称可以启发术语调查。每个候选独立通过对应领域判据，发现来源与领域结论分别保留。

对象登记后、共同语义核验前，使用 `ws.tool.groupQualityRuleEntries` 取得规范结构关系。glossary 的同类发现分组使用独立候选与 `seed: true` 既有条目；其余条目通过正式匹配参与参考与边界核验。text_preserve 使用实际调查集合。分析集合、目标筛选、分页、组和关系的含义遵循当前工具契约；保留 component 与跨组关系，按来源回流受影响对象。

结构关系说明共同核验原因，语义身份与最终合并由领域证据确定。存在影响合并、拆分、译名或消歧的实体关系时，编纂译文语言的实体关系图；关系过密时用主干图与关系表表达，多个语义簇按需要拆图。形成关系图和规则方案时取得的新事实继续进入自启发循环。

## 3. 领域对象与规则方案

共同 `scope`、`checks` 与 `targets` 遵循 `self-inspiring`。每个质量对象记录稳定键、`kind`、`origin: candidate / existing`、既有 `id`（如有）、证据与领域处置：

|字段|含义|
|---|---|
|`necessity`|`required / not_required / unknown`，表达对象资格|
|`resolution`|`direct / conditional / narrowed / split / blocked`，表达处理依据；条件使用适用于 glossary|
|`action`|候选为 `create / discard / blocked`；既有对象为 `keep / update / delete / blocked`|
|`seed`|既有 glossary 条目的发现资格，保留当前依据|

规则方案 `proposals` 保存稳定键、规则类型、字段、`covers` 对象键集合、命中与边界证据，以及 `candidate / selected / rejected` 状态。对象到方案的覆盖关系从 `covers` 计算，保留多条精确分支共同覆盖一个对象的能力。

glossary 方案记录原有覆盖与新增命中的分类，支持词根合并前后核对。text_preserve 方案记录每个表达式自身的完整扫描和安全结论。`required` 对象必须由选定方案覆盖，或有完整 `blocked` 说明；既有保留规则也进入最终集合的覆盖核对。

## 4. 目标集合验收

满足 `self-inspiring` 稳定条件后，构造目标规则集合并程序化核对业务结果：

- 目标、规则类型、既有规则策略与操作符合 scope，范围外规则保持证据身份。
- 既有 glossary 对象的 `seed` 与证据、处置一致，受启发候选具有独立资格证据；最终集合满足 `glossary-rules` 的安全覆盖与最小化条件，实体关系与方案一致。
- 每条 text_preserve 规则均按领域技能独立验收保护资格、表达式与命中安全。
- 既有集合、最终集合、字段、排序意图与 change 可对账，未决保持明确身份。

验收产生的增量按自启发协议回流，业务工作流保留已完成的领域结果。

## 5. 结果交付与提交核验

遵循 System Prompt 的结果表达，补充当前与目标规则数量、对象处置、覆盖关系及适用的实体关系图。

`report` 验收后交付方案；`change` 按完整范围统一提交。实际写入后核对规则覆盖、排序、重复与集合最小性，依据回执重建尚未落实的方案；用户要求或事实变化影响集合时重新验收并按自启发协议回流。最终报告实际写入与剩余目标。
